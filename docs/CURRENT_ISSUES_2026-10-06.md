## 范围与结论口径

## 1. T1→T2：发送返回到服务端读回调

**一句话问题：**10k/s 本机 WebSocket 压力测试中，客户端 send() 返回到服务端底层读回调开始，平均耗时 **19.014 µs**，是端到端路径中均值最大的相邻阶段。

**一句话根因：**本机发送之后，`kernel_task` 线程取得 CPU 并唤醒 QuantServer 的 I/O 线程；两次等待 CPU 和这段内核处理构成常态耗时的主要部分，同轮第二条消息还会等待前一条处理。

T1 = 客户端 send() 返回；K = 服务端 kevent 返回该 socket 的可读事件；T2 = 服务端底层 socket 读完成回调开始。这段结束时还没有进行 JSON 解析或策略处理。

### 三层证据

| 证据 | 使用的工具与定位方法 | 测到的结果 |
| --- | --- | --- |
| 正式 10k/s、30 秒轮次 | 原生发送器在 `send()` 返回后记 T1，`TimedTcpStream` 在底层读取完成回调入口记 T2；按帧序号配对。 | 298,995 帧；T1→T2 均值 **19.014 µs**、p50 **16 µs**、p99 **55 µs**。这是正式延迟口径。 |
| 两次同负载 K 探针复跑 | 仅在 QuantServer 中用 `DYLD_INSERT_LIBRARIES` 加载 `kevent_probe_darwin.cc`，在 `kevent` 返回 `EVFILT_READ` 后记录 K，按同一帧拆 T1→K、K→T2。 | 两轮有效配对 298,866/298,882 帧；T1→K p50 均为 **11 µs**，K→T2 p50 均为 **4 µs**。常态耗时主要位于 K 之前。 |
| 真实 QuantServer 内核跟踪 | macOS `ktrace` 在一轮真实 10k/s 运行中捕获 0.264 秒、335,269 条系统调用和调度事件；用原始 CSV、消息序号和服务端线程关联。 | 2687 条候选帧，2646 条与同线程 `kevent` 退出配对，**2619 条**具有完整的内核线程、I/O 线程和 `recvmsg` 事件。下表只使用这 2619 条。 |

### 这张表是怎么量出来的

1. **先量总时间。** 测试工具给每条消息编号；本机 `send()` 返回时记 T1。QuantServer 开始执行底层读回调时记 T2，并把编号和 T2 回给测试工具。同一编号的 T2 减 T1，就是这条消息的总耗时。
2. **再看中间发生了什么。** macOS 自带的 `ktrace` 像一台事件记录器：它记下唤醒服务端的内核线程何时获得 CPU、它何时叫醒 QuantServer 的 I/O 线程、I/O 线程何时获得 CPU，以及服务端何时开始和结束从 socket 取数据。不需要往内核里加日志。
3. **找到同一条消息。** 消息编号能查到它走哪个连接、交给哪个 I/O 线程。只用该线程上先后顺序合理、读取字节数也吻合的内核记录；对不上的丢掉。这段 0.264 秒的记录中，2687 条候选消息最终有 2619 条能完整拆分。
4. **对齐两套时钟，再相减。** 程序打点和系统记录的计时起点不同。我们额外记录“系统告诉服务端 socket 可读”的时刻 K，用它把两套时间对齐。K 只用来对时，**不代表数据刚进入接收队列**。对齐后，沿同一条消息的时间线，把相邻两个时刻相减，就得到下表七段耗时。

### 同一批 2619 条消息的延迟分账

| 相邻阶段 | 均值 µs | p50 µs | p99 µs | 时间点依据 |
| --- | ---: | ---: | ---: | --- |
| T1 → 内核线程获得 CPU | 1.805 | 1.421 | 5.713 | T1、`kernel_task` 线程 578 的 `MACH_DISPATCH` |
| 内核线程在 T1 后运行 → 唤醒 I/O 线程 | 2.960 | 2.750 | 6.713 | 线程 578 的运行时间、目标 I/O 线程的 `MACH_MKRUNNABLE` |
| I/O 线程可运行 → 获得 CPU | **4.777** | **3.041** | 37.750 | 同一 I/O 线程的 `MACH_MKRUNNABLE` → `MACH_DISPATCH` |
| I/O 线程获得 CPU → `kevent` 系统调用退出 | 0.589 | 0.459 | 2.042 | `MACH_DISPATCH` → `BSC_kevent` 退出 |
| `kevent` 退出 → `recvmsg` 进入 | 0.748 | 0.625 | 2.458 | 两个系统调用的内核时间戳 |
| `recvmsg` 进入 → 退出 | 0.878 | 0.792 | 2.916 | `BSC_recvmsg` 进入/退出 |
| `recvmsg` 退出 → 底层读回调 T2 | 5.267 | 2.204 | 81.162 | `BSC_recvmsg` 退出、T2 |
| **T1 → T2** | **17.024** | **12.000** | **100.000** | **上述 7 段均值来自同一批 2619 帧，逐段均值相加为 17.024 µs** |

这 2619 条消息的 I/O 线程唤醒事件都由 `kernel_task` 线程 578 执行。回看线程 578 最近一次变为可运行的事件，其中 2471 次由 `ws_sender` 触发、147 次由 `hquant_server` 触发、1 次由 `kernel_task` 触发；“最近一次唤醒来源”仅用于确认线程路径，不能当成每个 TCP 包的内核函数栈。

一条普通消息可直接核对：**序号 9442**，以 T1 为 0，内核线程获 CPU 为 +1.421 µs，唤醒 I/O 线程 +4.004 µs，I/O 线程获 CPU +6.921 µs，`kevent` 退出 +7.379 µs，`recvmsg` 进入 +8.004 µs、退出 +8.796 µs，T2 为 +11.000 µs。这个例子只展示事件如何相减，汇总数来自上表全部 2619 条。

上表两次等待 CPU 合计均值 **6.582 µs**；“可运行→获得 CPU”是等待调度，不是上下文切换代码执行了 4.777 µs。对 2510 条还能配到选择 CPU 事件的消息，唤醒→`MACH_SCHED_CHOOSE_PROCESSOR` 均值 0.125 µs，随后至实际获得 CPU 均值 4.496 µs。`recvmsg` 退出→T2 的 5.267 µs 均值包含同轮第二条消息：2521 条首个读回调这一段均值 2.311 µs，98 条第二个读回调均值 81.317 µs，后者在同一 I/O 线程上等待前一条处理。详见问题 3。

**结论与边界：**正式 30 秒轮次的 19.014 µs 和短跟踪窗口的 17.024 µs 来自不同测量条件，不能互相作精确分账。真实进程的短窗已经直接显示：内核线程执行事件交付、唤醒 I/O 线程及 I/O 线程等待调度，是常态耗时的主要位置；这不能单独证明 CPU 核数不足。当前 `ktrace` 没有 TCP 数据进入服务端接收队列和 `kqueue` 内部通知的时间点，因此还不能把 2.960 µs 内核执行段分成 TCP 处理与可读事件通知。要再拆这一段，必须在真实服务对应 socket 的这两个内核点打时间戳并按连接/序号关联，不能用 loopback `tcpdump` 时间代替接收队列入队时间。

**建议解决方案：**先对真实服务 A/B 测试发送器忙等与 I/O 线程 CPU 资源安排，比较内核线程和 I/O 线程两次“可运行→获得 CPU”以及 T1→T2。若仍需要定位 2.960 µs 的内部组成，再使用能看到 TCP 接收队列入队和 `kqueue` 通知的内核探针。

证据文件：`/private/tmp/hquant-phase-10k-20261006/result.json`（正式轮次）；`/private/tmp/hquant-kevent-10k-20261006-r2/result.json`、`/private/tmp/hquant-kevent-10k-20261006-r3/result.json`（K 复跑）；`/private/tmp/hquant-t1t2-kernel30/result.json`、`acks.bin`、`ws_sender.events`、`ws_sender.sent_ns.bin`、`ws_sender.write_ns.bin`（同一内核诊断运行）；`/private/tmp/hquant-t1t2-kernel-final.ktrace` 及导出的 `.csv`；`/private/tmp/hquant_t1t2_kernel_correlate.py`（原有相关脚本，七段表补充了线程 578 的调度配对）。打点代码：`hquant/bench/market/ws_sender.cc`、`hquant/bench/timing/kevent_probe_darwin.cc`、`hquant/src/base/net.h`、`hquant/bench/live_ws_bench.py`。

## 2. 测量扰动与毫秒级异常长尾

- **现象**：上述两次带 K 探针的有效复跑 p99 只有 52/50 µs，但全量平均为 30.62/51.35 µs，p999 为 6.33/9.40 ms；少量毫秒级事件显著抬高平均值。原始无 K 轮次平均为 19.014 µs。内核跟踪在 0.264 秒内产生约 33.7 万条事件；带内核跟踪的 30 秒运行 T1→T2 p99 升至 354 µs。
- **定位**：高频全局跟踪会扰动要测的调度。原生发送器在 30 秒运行中使用约 29.7–29.8 CPU 秒，近乎占满一个逻辑核；模拟 WebSocket 服务和 QuantServer 同机运行。当前没有证据把少量毫秒级长尾统一归因于发送器、服务器或操作系统。内核 `MACH_DISPATCH` 的运行线程在 `threadid` 字段；早期按 `arg1` 配对的调度统计不能使用。
- **建议方案**：把正式延迟采集与内核跟踪分开；逐轮保存 sender、mock server、QuantServer、SQLite writer 的 CPU 使用率，以及每秒发送迟到、T1→K、K→T2 和超过 1 ms 的消息序号。减少发送器长时间忙等，再用相同的节奏门槛做 A/B；必要时在独立测试环境复核。内核跟踪只保留最小事件过滤器和短窗口，并比较窗口内外的延迟，受扰动的窗口不进入正式汇总。
- **关闭标准**：至少 3 次相同配置的正式运行能够复现均值和 p99/p999；每个毫秒级离群样本能定位到发送迟到、接收调度、同线程排队或其他明确阶段。

## 3. 同一 I/O 线程的短时队头等待

- **现象**：短内核跟踪中有 100 条消息的 K→T2 超过 50 µs。这 100 条全部对应一次 `kevent` 返回两个可读事件；同一工作线程执行两次有效 `recvmsg`，并在第二条读回调前发送了前一条的完成 ACK。典型样本中，第二条数据已读出，读回调仍等待约 80 µs。
- **定位**：1000 个 Shard 分配给 8 个 `io_context` 工作线程，每线程约负责 125 只股票。同一线程上的回调串行运行；在上述诊断样本里，第二个回调排在前一个消息处理之后。这**不等于**线程持续处理不过来：30 秒 299,000 条计时消息全部完成，也未据此证明正式轮次的 19.014 µs 主要来自此处。
- **建议方案**：先在无内核跟踪的正式轮次记录每个工作线程的就绪事件数、回调排队时间和上一条处理区间，确认队头等待的频率及其对 p99 的贡献。若确认超出目标，再 A/B 比较工作线程数、连接分配，以及把耗时较长的行情处理从 I/O 回调移到有界队列；必须保持每只股票的顺序和正确性。
- **关闭标准**：明确正式压力轮次中受队头等待影响的消息数、等待分布及优化前后端到端延迟，而非只引用受跟踪影响的 100 条样本。

原始跟踪：`/private/tmp/hquant-t1t2-kernel-final.ktrace`；对应运行：`/private/tmp/hquant-t1t2-kernel30/result.json`。

## 4. 压力 case 未覆盖模拟成交（已修复）

- **原问题与根因**：旧压力数据的公开成交始终发生在买一或卖一，而策略报价距对应成交价 9–14 个 tick。旧轮次虽收到 60,000 笔公开成交，Paper 成交记录却为 0；测试数据没有触发撮合。
- **改动**：固定 100 只股票挂 2 股买单和卖单，报价位于买一、卖一，每笔公开成交 1 股；每只股票的前 4 笔成交依次触发 2 次部分成交和 2 次完全成交。其他 900 只维持原负载。历史校验按股票核对预期成交笔数、方向、价量、费用、剩余量和整数账本，0 成交现在会直接失败。
- **验证**：最终 1000 只、30 秒 WebSocket 轮次发送 299,000 条计时消息并收到全部完成通知，实际 **400 条 Paper 成交、200 次部分成交、200 次完全成交**，与 fixture 预期一致；38,200 条历史记录无缺口，发送节奏和正确性门槛均通过。

证据：旧轮次 `/private/tmp/hquant-phase-10k-20261006/history.sqlite`；新轮次的[原始结果](STRESS_FILL_RUN_2026-10-06.json)和本机 `/private/tmp/hquant-fill-final.45iiIC/history.sqlite`。新负载的延迟须使用新轮次，不能与旧无成交负载直接相减。

## 5. SQLite 停机记录混入运行期统计（已修正）

- **原问题与根因**：旧轮次把停机撤单也纳入 40,000 条记录的统一分位数，得到入队→提交 p99 **37.41 ms**、入队→写线程开始 p99 **37.07 ms**。核对历史时间发现，两次 15 秒刷新各产生 14,000 条记录、分散在约 1.2 秒；真正密集的是停机时 6,000 条撤单及余额记录在 **7.63 ms** 内入队，与队列峰值 5036 和数十毫秒等待吻合。旧文档将主因归为同步刷新不准确。
- **改动**：记录每条历史的入队阶段；默认 `sqlite_queue_wait` 和 `sqlite_enqueue_to_commit` 只统计停机前入队的记录，并另列 `*_after_stop` 与 `*_all`。队列峰值也按停机前、停机后分列。写线程仍按最多 64 条一批异步提交，停机时完整排空。
- **验证**：最终 30 秒轮次中，停机前 **32,800** 条、停机后 **5,400** 条；入队→写线程开始 p99 分别为 **0.640 ms / 24.546 ms**，入队→提交 p99 分别为 **0.923 ms / 24.788 ms**，队列峰值分别为 **142 / 4093**，历史无缺口。这里的“停机前”还包含初始化记录，并非严格的计时发送窗口。

证据：[新轮次原始结果](STRESS_FILL_RUN_2026-10-06.json)的 `probe`；运行期间与停机期间的持久化时效应分别设目标。

## 6. NYSE、SSE 网络行情 case 尚无合格的性能轮次

- **现象**：已存档的 3 分钟 NYSE、SSE 本机 WebSocket 轮次最终状态正确，但按现行门槛（全局发送迟到 p99≤1 ms）分别测得 2.254 ms 和 4.774 ms；最差一秒的 p99 分别为 6.449 ms 和 31.169 ms。现有结果可用于正确性，不应作为可靠的市场 case 延迟或 QPS 结论。
- **定位**：这两轮发送节奏失真；原始脚本使用的发送实现、启动和预热路径也与后续压力正式轮次不同。不能仅因平均消息率较低就推断它们已经满足性能门槛。
- **建议方案**：用与当前压力测试相同的原生发送器、完成通知和预热口径，按各自真实 3 分钟节奏重新跑，每组至少 3 次；每次先检查逐秒发送节奏和消息/历史正确性，再汇总延迟。
- **关闭标准**：每个 case 均有通过节奏与正确性门槛的重复运行，并公布原始轮次而非只留下通过筛选的摘要。

证据见 [TEST_REPORT_DATA_2026-10-06.json](TEST_REPORT_DATA_2026-10-06.json) 的 `report_paced_valid` 与 `report_worst_second_p99_us`。

## 7. 10k/s、20k/s、40k/s 的测试器未完全统一

- **现象**：现有汇总中，10k/s、40k/s 使用原生发送器和完成通知接收器；20k/s 使用 Python 测试器。三组的 T0 边界和发送开销不同，跨速率的端到端延迟差值不能直接解释为 QuantServer 的扩展性。
- **定位**：这是测试工具口径差异，不是已经证明的 QuantServer 性能退化。[现有报告](TEST_REPORT_2026-10-06.html) 已说明该限制。
- **建议方案**：三档负载统一使用同一原生发送器、相同预热、ACK、探针开关和发送节奏门槛；分别报告测试器 CPU、发送迟到及 QuantServer 的服务端处理延迟。
- **关闭标准**：三档各有多次同口径有效运行，才能用 QPS 与延迟曲线判断容量拐点。
