# hquant 与成熟交易系统的差距

本评估以单交易所、单账户的现货做市系统为参照。它讨论系统的交易正确性和运行可靠性，不评价策略是否赚钱。

> 本文是首轮设计前的差距分析；当前代码进展与剩余门禁见[后续开发记录](TRADING_CHAIN_FOLLOWUP.md)。

## 当前项目处于什么阶段

项目已有公开行情的快照与增量同步、盘口过期检测、定点数计算、确定性回放、Paper 撮合、SQLite 历史，以及 1000 标的、30 秒的行情压力 case。这些是扎实的行情和模拟交易基础。

当前仍只支持模拟盘。`PaperExchange` 保存订单和余额；`Executor` 直接调用它；`Shard::OnAccountEvent` 收到回报后主要写历史。配置会拒绝 `live`。因此，增加外部订单 socket 后，项目可以验证外部交易链路，但还不能据此视为可安全运行的实盘系统。

相关代码：[Executor](../hquant/src/shard/executor.cc)、[账户事件](../hquant/src/shard/shard.cc)、[配置校验](../hquant/src/config.cc)、[现有设计](DESIGN.md)。

## 1. 账户级订单管理系统是最大的架构缺口

需要在 Shard 与交易适配器之间增加按账户串行处理的 OMS。OMS 保存本地订单投影、成交、资金预留、活动订单、未知结果和对账状态。策略从 OMS 取得账户视图；Paper 撮合器与实盘适配器都向 OMS 送标准化事件。模拟交易所仍应保有自己独立的账本，以便核对。

提交命令要区分本地拒绝、已入队、可能已发出、交易所确认、交易所拒绝。撤单请求要单独跟踪，因为撤单途中仍可能成交。回报可能重复、乱序，或先于请求响应到达；必须按交易所执行 ID 去重，并以累计成交量和剩余量校验状态转换。`client_order_id` 要跨 shard、账户和进程重启保持唯一，交易所订单 ID 单独保存。

当前设计文档认为实盘主要是替换 `PaperExchange`。这一前提应改为先建立 OMS，再接适配器。

## 2. 事前风控目前过于薄弱

当前 `Executor` 校验价格和数量步长、最低数量与金额，以及单资产的余额和额度。共享账户之后，还需要在账户级原子地检查并预留资金，防止多个 shard 同时花费同一笔余额。

实盘前至少定义：单笔最大金额、价格相对可信行情的偏离上限、单标的与账户总敞口、最大活动订单数、下单和撤单速率、连续拒单或亏损阈值，以及暂停新单和紧急撤单动作。公开行情或私有回报连接不健康时，应禁止新单；撤单和对账仍需继续运行。

## 3. 断线与重启后的恢复机制尚不存在

交易请求超时不能直接判失败；私有流断线后也不能假设没有成交。OMS 需要定期及在故障后查询交易所的活动订单、成交和余额，补漏、去重、修正本地账本。只有对账完成且两条数据通道健康，才恢复新单。

进程启动时，应先恢复本地订单意图和上次已知状态，再查询交易所，处理“本地有而交易所无”和“交易所有而本地无”的订单。停止时要等待撤单结果或完成对账，不能发出异步撤单后直接结束工作线程。

交易所协议可能明确规定超时为“执行状态未知”。例如 [Binance Spot REST 文档](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md)要求先看私有流，仍无结果再查询订单。[FIX 订单状态示例](https://www.fixtrading.org/online-specification/order-state-changes/)也涵盖撤单待确认、撤单拒绝和期间成交。

## 4. 当前 SQLite 历史不能承担实盘恢复职责

现有历史表记录命令和回报，按 shard 编序；实时写队列满时允许丢记录并写 `history_gaps`。它适合观察和压测核对，不能作为唯一可恢复的订单事实来源。

实盘需要可靠的发送意图日志：在可能发往交易所之前保存订单 ID、账户、标的、命令及状态；回报应用和资金变化应可重放，必要时配合快照。持久化故障应触发停止新单，而不是继续交易并留下不可恢复的历史缺口。审计历史可以继续异步写，但不能替代恢复日志。

相关代码：[历史记录与队列](../hquant/src/sqlite_history.h)、[实时队列行为](../hquant/src/sqlite_history.cc)、[启动与停止](../hquant/src/runtime.cc)。

## 5. 交易所适配器不止是收发 socket

选定目标交易所和订单协议后，适配器还需管理认证与签名、时钟校准、连接心跳、重连、请求限速、退避、订单和查询额度，以及动态交易规则和手续费信息。账户级队列应为撤单与对账保留处理能力；队列满时要明确拒绝新单并释放本地预留。

本地模拟交易所可复用目标协议来验证解析与时序，但 1000 个合成标的及本机 socket 的结果不能代表真实交易所的可用标的、限额或网络延迟。目标交易所的实际规则以其官方文档为准。例如 [Binance Spot REST 文档](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md)列有请求权重、订单数和限流响应。

## 6. 运行控制和可观测性不足

当前 Control 提供 shard 状态、历史、策略参数更新和停止。成熟运行环境还应可见：账户和私有流健康、各订单状态数量、未知结果、对账差异、发送队列深度、交易所拒单与限流、行情及回报延迟、SQLite 写入健康。

操作动作应分开：暂停新单、继续管理现有订单、撤全部单、查询对账、恢复交易、正常停机。每项动作及配置变更要有时间、操作者、理由和结果的审计记录。凭据权限、保存位置和轮换也需要设计。

## 7. 测试范围需要覆盖故障，而不只是吞吐

现有 1000 标的、30 秒 case 适合作为第一轮正常负载验证。新增独立模拟交易所后，要逐单核对模拟账本、OMS 最终状态和 SQLite，并分别统计行情处理、命令排队、发包、交易所接收、回报应用的延迟与 QPS。

随后加入故障脚本：提交后丢响应、重复或乱序回报、私有流断线、撤单与成交竞态、队列满、限流、磁盘写失败、发单前后崩溃和重启恢复。再做长时间运行与小规模非生产环境验证。30 秒正常运行成功只能证明该负载下的链路行为。

## 8. 策略质量需要单独评估

现有策略按中间价和固定价差双边挂单；Paper 模型对排队位置、成交和市场冲击有明确简化。成熟做市还需要库存管理、费用和滑点、逆向选择、净收益及风险调整后收益评估。这属于交易策略研究，和 OMS 正确性分开验收。

## 建议的设计顺序

1. 定义账户级 OMS、订单及撤单状态、资金预留和风控门禁。
2. 让 Paper 与实盘适配器通过同一事件接口驱动 OMS。
3. 选定目标协议，接异步交易客户端与独立模拟交易所。
4. 用现有 1000 标的、30 秒 case 验证外部链路、账本一致性和分段性能。
5. 增加恢复日志、故障对账、运行控制及故障注入，作为实盘前验收。

**结论：**这份方案是从模拟盘走向外部交易链路的正确第一步。成熟度上的关键跃迁是建立账户级 OMS、可靠恢复和风控门禁；单纯替换 `PaperExchange` 或跑通 30 秒压测都不足以覆盖这三项。
