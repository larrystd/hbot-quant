1. 测试数据

全部是确定性合成行情，使用 1000 只股票。回放源的每条盘口消息含买 10 档和卖 10 档的完整价量；转换为 WebSocket depthUpdate 时，还可能附加零量删档。每笔成交是独立消息，含成交 ID、价格、数量和主动方向，不含盘口档位。

10k/s、20k/s、40k/s 表示全部 1000 只股票合计的目标行情消息数/秒；盘口消息和成交消息各算一条。三组均发送 30 秒。每只股票的盘口序号、成交 ID 连续，股票之间错峰发送。

为何计时消息数少 1000？每只股票的第一条盘口共 1000 条先用于建盘预热，不计入延迟和 QPS；其余消息按上表节奏计时发送。

每只股票的盘口/成交消息间隔分别为：10k/s 为 125/500 ms，20k/s 为 62.5/250 ms，40k/s 为 31.25/125 ms；1000 只股票错开这些间隔发送。

这些是合成行情，不是录制的交易所数据。消息格式见 测试数据定义，生成逻辑见 make_market_cases.py。

2. 测试方法

  1. 链路：测试器按计划时间经本地 WebSocket 发送行情 → quantserver 收齐帧并解析 → Shard 同步处理 → 服务端发送一条 UDP 压测完成通知 → 测试器收到通知。每只股票的 REST 快照和首条盘口预热在计时前完成。
  2. 压测完成通知：报告旧数据字段名为 ACK。它是压测代码为每条行情额外发的 UDP 小包，里面有消息序号和时间戳，只表示同步行情处理走到了测量终点；它不是交易所接收订单、成交或撤单回报，也不是生产业务消息。
  3. 端到端延迟：测试器调用发送接口前 T0，到测试器从 UDP socket 取到对应完成通知 T9。10k/s 与 40k/s 的 T0 在原生 send() 前；20k/s 的 T0 在 Python StreamWriter.write() 前。包含本机传输、两侧调度和测量通知回程。
  4. 服务端延迟：Beast 读完完整 WebSocket 帧 T3，到同步行情处理完成 T6。包含 Feed 接收、JSON 解析以及 Market、Paper、账户、策略和执行；SQLite 写线程的提交不在此区间内。
  5. 吞吐：完成 QPS = 计时消息数 ÷ 服务端首条计时帧在 Feed 打点 T4 到末条处理完成 T6 的窗口。每组预热 1000 条盘口，因此计时帧数比生成总数少 1000。
  6. 正确性：逐条核对消息 ID 与唯一完成通知，并独立检查最终十档盘口、成交摘要、订单状态、余额、手续费、SQLite 行数与历史序号。

单条消息的打点顺序：端到端 T0→T9 包含三段：发出与收齐帧 T0→T3、服务端同步处理 T3→T6、压测完成通知回程 T6→T9。下方完整细分针对原生发送器的 10k/s 轮次；每个相邻区间只出现一次。kqueue 的额外打点只用于另一轮诊断，放在 T1 与 T2 之间。

节奏合格条件：正确性通过；发送落后全程 p99 ≤ 1 ms；最差一秒的发送落后 p99 ≤ 10 ms；末条发送不晚于计划结束 10 ms。旧结果也按这套统一条件重判。

汇总表选用的 10k/s、40k/s 轮次使用原生发送器和完成通知接收器；20k/s 使用 Python 测试器。三组均按逐条完成通知计时。测试器实现不同，不用跨速率的端到端延迟差值推断服务端性能变化。下方 kqueue 分段来自另一轮有效 10k/s 诊断，只用于定位同一帧的事件边界，不能与主轮次的分段相加。

4. 测试分析

  1. 吞吐与正确性：三组各持续 30 秒，最终消息、盘口、成交、账本和历史核对通过，实际完成约 1 万、2 万、4 万 QPS。40k/s 是一轮有效结果，尚不能据此给出最大稳定容量。
  2. 端到端主要耗时：在完整分段的 10k/s 轮次中，T1→T2 均值 19.014 µs；kqueue 诊断把这一段的常态位置分为 T1→K 的 p50 11 µs 和 K→T2 的 p50 4 µs。主要等待发生在 kqueue 报告可读之前；打点没有继续区分 TCP 内核交付、线程唤醒和系统调度，不能把整段归因于 Asio。
  3. 服务端同步处理：T3→T6 均值 5.987 µs、p99 21 µs；其中 JSON 解析均值 2.382 µs，T5→T6 均值 2.884 µs。完成通知仅为测试计时，T6→T9 不属于行情处理；T7 是发包前打点，不表示 UDP 包已经发出。
  4. 异步持久化：40k/s 的历史入队→提交 p99 为 50.45 ms，主要等待在 SQLite 队列。同步行情处理不等待写盘，持久化时效需单独评价。

测试环境是本机 loopback、无 TLS、合成行情和 PaperExchange。当前主机没有 Linux perf 或 Xcode xctrace；DTrace 初始化被系统权限拒绝。本报告据同帧 kqueue 打点定位事件边界，没有把尚未区分的内核与调度时间写成已确定原因。
