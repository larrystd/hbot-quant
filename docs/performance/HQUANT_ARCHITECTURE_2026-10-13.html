hquant 架构：路径与模块

本文按 hquant/src 当前代码写成（约 1.1 万行，Bazel 构建）。分三篇：路径篇讲一条消息或一笔订单在系统里怎么走；异常篇按"异常、行为、处理与恢复"讲出错时系统做什么；模块篇讲每个文件负责什么、归哪个线程、守哪些规则。

代码位置写作 目录/文件:行号，相对 hquant/src/。

0总览

hquant 是一个做市进程：每个 Shard 负责一个交易对，接 Binance 公开行情，用一个简单的双边挂单策略产生订单；订单经 TradingAccount 和 TradePort 发给交易所。交易模式只有两种模拟：PressureSim（连本地模拟交易所 bench/venue，压测用）和 OnlineSim（连 Binance Spot Demo，虚拟资金），见 config.h:44。

分层与依赖

依赖只能从上往下。trading/ 不认识 Binance，只认识抽象接口 TradePort；venue/binance/ 实现这个接口；runtime 在启动时把两边接起来。

main.cc
  └─ runtime            组装：创建线程、账户、Shard、交易客户端，连好回调
       ├─ control_server   Unix socket 控制面
       ├─ sqlite_history   观察用历史（可丢，异步）
       ├─ replay_reader    文件回放输入
       ├─ shard/           行情 → 策略 → Shard 本地交易状态
       │    └─ 依赖 trading/（含具体类 TradingAccount）
       ├─ venue/binance/   TradePort 的 Binance 实现：REST、私有流、签名、限频
       │    └─ 依赖 trading/trade_port.h
       └─ trading/         与交易所无关：订单状态机、资金、风控、可靠日志、账户
            └─ base/       定点数、ID 类型、网络、日志

线程模型

理解 hquant 最关键的一张表。每个对象只归一个线程所有，跨线程基本都靠 boost::asio::post 投递任务。线程在 runtime.cc:195 的 Runtime::Start 里创建。

线程数量拥有/运行的东西
Shard workermin(8, shard 数)多个 Shard 共用一个 io_context。行情协程（BinanceFeed）、Market、Strategy、ShardTradingState；以及绑定到这个 worker 的 BinanceTradeClient 的 REST 连接（下单请求在这里写出）。
Account workermin(2, 账户数)TradingAccount 的任务队列、对账副本（OrderManager + FundsState）、AccountSync、AccountViewPublisher、REST 回调。空闲时先忙等 50 µs 再睡（RunAccountContext，runtime.cc:44）。
私有流线程每账户 1 个Binance user data WebSocket（BinanceUserStream），只在第一个 BinanceTradeClient 上开启。
REST 线程0 或 1 / client只有不绑定 Shard worker 的 client 才自建（账户下没有 Shard 时）。
OrderJournal1SQLite 可靠日志写线程，凑批提交（最多等 250 µs 或 256 条）。
SqliteHistory1 写 + 1 读观察用历史记录，异步写入。
ControlServer1Unix socket，按行读 JSON 请求。
主线程1回放模式下逐条读文件；实时模式下等待信号。

实线：同线程调用或 post；虚线：私有回报；红线：可靠日志。图里省略了控制面和历史记录线程。

三条贯穿规则

① 单线程所有权Shard 的状态只在 Shard 线程改，账户的状态只在账户线程改。别的线程想改，就 post 一个任务过去。例外只有一处：SubmitFromShard/CancelFromShard 在 Shard 线程直接调用账户方法，靠锁和"只入队、不改状态"保证安全。
② 先日志，后状态交易所来的事实（请求结果、回报、成交、余额、查单结果）先写 OrderJournal，COMMIT 成功后才应用到状态（trading/trading_account.cc:944）。进程崩溃后靠日志重建。
③ 热路径本地准入账户的资金在启动时就按 Shard 切好（ResolveShardAllocations）。下单时 Shard 只查自己那一份，不用等账户线程回话；账户线程事后异步更新自己的对账副本。

A路径篇：一件事在系统里怎么走

每条路径按时间顺序列步骤，标出执行线程和代码位置。建议按 A1 → A2 → A3 → A4 → A5 的顺序读，后面几条是在这几条基础上的分支。

A1 启动与就绪

目标：进程起来之后，Shard 什么时候才允许下第一笔单。答案：私有流连上并完成一次全量对账之后。

  1. 主线程 main.cc:487 解析 gflags（--config、--state_dir、策略覆盖参数、压测参数），LoadConfig 读 YAML 并校验，然后构造 Runtime。
  2. 主线程 Runtime 构造（runtime.cc 约 95–190 行）：
    • 创建 SqliteHistory（容量 max(8192, shard 数×64)）、OrderJournal（与 history 同目录的 order_journal.sqlite）、ControlServer（把各个控制请求接到 Runtime 的成员函数上）。
    • 算线程数：账户 worker min(2, 账户数)，Shard worker min(8, Shard 数)；每个线程一个 io_context。
    • ResolveShardAllocations（config.cc:539）把每个账户的资金切给它的 Shard：显式配置的先扣，剩下的在相关 Shard 间平分（余数给前几个）。
    • 账户轮流分到账户 worker；Shard 按"同一账户内轮转，可用 worker 数 = min(Shard worker 数, rest_connections)"分到 Shard worker。
    • 对每个 Shard 调 account->SetViewSink 和 SetTradeSink：账户以后要通知这个 Shard 时，就调这些 lambda，lambda 内部是 Shard::PostXxx，即 post 到 Shard 线程。
  3. 主线程 恢复（Runtime::Start，runtime.cc:195）：journal_.Start()，对每个账户 journal_.Load(id) 读出全部日志条目，先 TradingAccount::RestoreJournal，再对该账户的每个 Shard 调 RestoreTradingJournal。两边各自从同一份日志重建自己的订单和资金状态。
  4. 主线程 建交易客户端：所有账户共用一个 RequestScheduler（限额取各账户配置里最小的非零值）。对每个账户，按它的 Shard 所在的 Shard worker 建一个 BinanceTradeClient，REST 连接数在这些 client 间平分，REST 协程跑在对应 Shard worker 的 io_context 上；只有第一个 client 开私有流、拉交易规则。SetPort/AddShardPort/SetShardPort 记下"哪个 Shard 用哪个 client"。
  5. 主线程 启动 history 线程和所有 io worker 线程；shard->Start()：实时模式下 co_spawn(market_.RunBinance()) 并启动策略定时器（shard/shard.cc:57）。然后给每个 Shard 投递一份初始 AccountView，最后启动控制面。
  6. 私有流线程 user stream 连上，回调 on_health(true) → TradingAccount::OnConnectionState（trading/trading_account.cc:920）。不在账户线程就先入队转过去。
  7. 账户线程 SyncFromVenue → AccountSync::Start（trading/account_sync.cc:54）：关准入，依次查交易规则 → 挂单 → 逐单查单和成交 → 余额。每一条查到的事实都走 PersistAndApply（先日志再应用）。
  8. 账户线程 FinishSync（account_sync.cc:387）：如果对账期间又来了私有回报，就整轮重来（最多 3 次）。否则 ready = true，EnableAdmission()，并把 min_ready_revision_ 设成当前视图版本，再发布全部视图。60 秒后再做一次周期对账。
  9. Shard 线程 收到 ready=true 且版本 ≥ min_ready_revision_ 的 AccountView。从这一刻起，RunAccountDecision 的门控才放行。
为什么要比较视图版本：准入是原子变量，Shard 却是凭自己手里的 AccountView 来下单的。如果 Shard 手里还是对账前的旧视图，就算准入已经打开，AdmissionEnabled(view_revision) 也会因为版本太旧而拒绝。

A2 行情：一帧 WebSocket 消息怎么变成策略调用

整条路径都在同一个 Shard worker 线程上同步完成，中间没有队列。

  1. Shard 线程 BinanceFeed::RunCycle（shard/binance_feed.cc:350）是一个协程。每次（重）连接先 ++epoch_ 并发出 FeedConnected{epoch}，然后连 WebSocket。
  2. 先读 WS，直到拿到第一条 depthUpdate，记下它的 first_sequence（这期间的成交照常转发）。
  3. 再发 REST GET /api/v3/depth 拿快照（最多 3 次）。如果快照比第一条增量还旧（last+1 < first_update）就重拿。遇到 429/418 记下退避时间。
  4. 进入主循环：每帧用 simdjson 解析，按 e 字段分成 BookDiff 或 PublicTrade。价格和数量在解析时就换算成整数 tick/lot。
  5. 调 on_input_ → Market::HandleInput（shard/market.cc:241），按类型分派：
    • OnDiff：Live 时检查序号是否接得上（first ≤ seq+1）。接得上就 OrderBook::ApplyDiff，更新 BookView，发 BookChanged。Syncing 时先缓冲，交给 ApplyBuffered 等快照对齐。
    • OnSnapshot：只在 Syncing 时有效，重建盘口后接缓冲的增量，至少接上一条增量才切到 Live。
    • OnTrade：不改盘口，只更新 last_trade，发 PublicTrade 通知。
  6. 出现序号缺口、盘口交叉或单边为空、缓冲满、市场不匹配时，EnterSyncing(reason, reconnect=true)：清空盘口，设 needs_resync_。on_input_ 把这个标志返回给 Feed，Feed 结束本轮，等退避后重连（回到第 1 步）。之前是 Live 的话，还会发一次 BookUnavailable。
  7. 另有 StaleLoop 协程，周期为 min(stale_after_ms/2, 1s)。Live 状态下超过 stale_after_ms（默认 5 s）没更新，就进入 Syncing 并取消 WS 读，触发重连。
  8. notify_ → Shard::OnMarket（shard/shard.cc:306）→ RunStrategyDecision。每次盘口变化和每笔公开成交都会让策略跑一次，策略自己靠 refresh_ms 节流。

A3 下单：从策略决定到 HTTP 请求写出

这是延迟最敏感的一段，几乎全部在 Shard 线程 上完成。

  1. 门控（shard/shard.cc:77）：以下任一成立就直接返回：有提交或撤单还在等确认（trading_.Pending()）；account_view_.ready 为假；AdmissionEnabled(revision) 为假。所以同一个 Shard 同一时刻只有一批请求在途。
  2. 组装 ExecutionView：活跃订单 ID、本 Shard 的 base/quote 可用额和预算（来自 ShardTradingState 自己的余额，不读账户线程的数据）、手续费率、价格和数量精度、最小下单量和最小下单金额。
  3. 策略 Strategy::Decide（shard/strategy.cc:11）。逻辑见 A6，输出 SubmitOrders{买单, 卖单}。
  4. 生成客户订单号 NewClientOrderId（trading/client_order_id.cc）："hq" + 16 字节随机数的十六进制，共 34 个字符。
  5. 本地准入 ShardTradingState::BeginSubmit（shard/trading_state.cc）：
    • RiskLimits::Check：价格和数量精度、最小下单金额、交易所当前规则（VenueRule）、单笔金额上限、活跃订单数、同一计价资产的挂单总值。检查对象是本 Shard 自己的订单表。
    • ReserveAmount：卖单占用 base 数量；买单占用 ceil(价×量) + ceil(手续费)，费率非零时再加一点余量。
    • Reserve：从本 Shard 的额度里扣出这笔占用，不够就拒绝。
    • 本地订单号 = (shard_id+1) << 40 | 序号，订单以 PendingSubmit 状态记入 OrderManager。
  6. 交给账户 TradingAccount::SubmitFromShard（trading/trading_account.cc:152），仍在 Shard 线程上执行：
    • 加读锁 admission_gate_mutex_，再查一次准入和视图版本；选 TradePort（优先用本 Shard 绑定的那个）。
    • OnlineSim 模式下用 CAS 检查本次运行的下单次数上限（max_submissions_per_run）。
    • TryEnqueue(镜像任务)：往账户队列放一个 lambda，稍后在账户线程上执行 funds_.ReserveAllocated + order_manager_.Begin + 写历史 + 刷新视图。
    • Persist(SubmitIntent)：给日志条目编序号，journal_->Append 只入队，落盘结果稍后回调。
    • port->Submit(command, done, write_started)。
    任何一步失败都会回滚：Shard 侧 AbortSubmit 释放占用；账户侧补一个 abort 镜像任务，必要时写 SubmitAbort。
  7. REST 排队 BinanceTradeClient::Enqueue（venue/binance/trade_client.cc:309）：队列容量按类型留了余量（下单最多用到 容量 − 2×容量/8，撤单最多用到 容量 − 容量/8），保证队列快满时撤单和查询仍能进来。因为 REST io 就是当前 Shard worker，直接 QueueOnRest，放进 6 个优先级队列之一（撤单 > 查单 > 查成交 > 挂单/规则 > 余额 > 下单），然后为空闲的连接 co_spawn(Drain)。
  8. 发送 Drain（trade_client.cc:554）：取最高优先级的请求。下单在队列里超时（PressureSim 30 s，OnlineSim 5 s）就直接返回 NotSent。scheduler_->Reserve 预扣请求权重和下单次数，不够就等定时器。MakeRequest 用 HMAC 签名，然后 co_await http.Send。开始写 socket 的那一刻，on_write_start 把 write_started post 到账户线程（见 A4）。
两份订单状态：这笔订单此刻同时在 Shard 的 ShardTradingState（决定能不能再下单）和账户的 OrderManager（与交易所对账、查单）里。两份都由同一串事件推进：账户先收到并落日志，再通知 Shard。

A4 请求结果回程：HTTP 响应 → 账户 → Shard

  1. Shard 线程 结果分类 BinanceTradeClient::Complete（trade_client.cc:660）把 HTTP 结果归为 4 种 TradeResponse::Result：
    情况结果
    网络错误，且还没开始写NotSent（确定没发出）
    网络错误，已开始写；或 5xx/408/429/418；或响应体表明执行状态未知Unknown（可能已成交，需要查单）
    其它非 200：下单Rejected
    其它非 200：撤单Unknown（撤单失败不代表订单状态确定）
    200 且客户订单号一致Confirmed + 交易所订单号；撤单还会带回剩余数量 = origQty − executedQty
    然后 CompleteTrade 把 done post 到账户 io。
  2. 账户线程 done → TryEnqueue(PersistSubmitResponse)，经 Drain 在状态锁下执行。
  3. 账户线程 PersistSubmitResponse（trading/trading_account_journal.cc:41）写 SubmitOutcome。
  4. 日志线程 凑批，BEGIN IMMEDIATE … COMMIT（trading/order_journal.cc:287）。提交后把回调 post 回账户 io。
  5. 账户线程 提交成功后两件事：
    • NotifyResponse → TradeSink → Shard::PostTradeResponse，post 到 Shard 线程。
    • SubmitResponse（trading_account.cc:708）更新账户副本：NotSent 释放占用；Unknown 标记 submit_unknown 并安排查单；Rejected/Confirmed 转成一条 OrderReport 应用。如果私有回报已经先到了，迟到的 HTTP 超时不会把已确认的订单改回未知。
  6. Shard 线程 ShardTradingState::ApplyResponse（shard/trading_state.cc）按同样的规则推进 Shard 侧订单；订单进入终态就释放占用。Pending() 变为假后，下一次行情或定时器触发就能再做决策。

写出通知这条支线：on_write_start → 账户线程 OnWriting（trading_account.cc:853）：标记 submit_writing，Arm 一个 2 秒后的查单计划，写 SubmitWriting 日志；再 NotifyWriting → Shard MarkWriting。有了这个标记，"请求根本没发出"和"已经写到网络上但结果未知"就能区分开：已经 writing 的订单如果收到 NotSent，会被当作数据错误。

A5 私有回报：交易所推送 → 账户 → Shard

  1. 私有流线程 BinanceUserStream 用签名方式订阅 userDataStream.subscribe.signature，ParseBinanceUserFrame 解析出 AccountEvent：executionReport → OrderReport，有成交时再加一个 Fill；outboundAccountPosition → BalanceUpdate；balanceUpdate/externalLockUpdate → BalanceDelta。
  2. 私有流线程 TradingAccount::OnVenueEvent（trading_account.cc:1124）：++pending_private_events_，TryEnqueue。队列满就暂停账户（Pause），要求重新对账。
  3. 账户线程 正在对账时，事件先存进 AccountSync 的缓冲（对账结束时如有缓冲就整轮重来）；否则调 PersistAndApply(event, from_venue=true)。
  4. 日志线程 写 OrderReport/Fill/Balance/BalanceDelta 条目并提交。
  5. 账户线程 提交成功后 ApplyEvent（trading_account.cc:1143）：
    • OrderReport：order_manager_.ApplyReport 推进状态；订单未终结时 funds_.MarkVenueAccepted，表示交易所的 locked 余额已经包含这笔占用。
    • Fill：成交 ID 去重，FundsState 记成交借记和投影总额。
    • BalanceUpdate：和"成交推算出来的总额"对比；乱序的旧余额回报直接忽略。
    • 来自交易所的 BalanceDelta（外部充提或锁定）：直接暂停，要求重新对账。
    • 最后调 NotifyEvent：只有 OrderReport/Fill 会转给订单所属的 Shard。
    之后 ScheduleOrderQuery()、FlushViews()。
  6. Shard 线程 Shard::PostTradeEvent（shard/shard.cc:184）→ ShardTradingState::ApplyEvent：
    • 回报：订单进入终态就释放占用。
    • 成交：在本 Shard 的余额上，买单扣 quote 加 base，卖单反过来，再扣手续费；然后把占用缩到剩余数量对应的金额。
    Shard 侧任何一处不一致（比如成交超出了本 Shard 的额度）都会 ReportShardError：账户关准入并暂停，这个 Shard 停止。
  7. Shard 线程 如果正在等撤单完成（awaiting_cancel_），并且已经没有在途请求、也没有挂单，就立刻再跑一次策略（见 A6）。

账户视图：FlushViews → AccountViewPublisher::Flush（trading/account_view_publisher.cc:79），只给"脏"的 Shard 发一份新 AccountView（版本号 +1）。视图包含 ready、交易规则、手续费、挂单和撤单状态、账户余额。Shard 在 OnAccountView（shard/shard.cc:262）里丢弃比手里更旧的版本。

A6 刷新循环与撤单：策略如何"撤旧挂新"

策略本身是无状态的纯函数，只记一个 next_refresh_at_。Strategy::Decide（shard/strategy.cc:11）的判断顺序：

  1. 盘口不是 Live：有活跃订单就全部撤（CancelOrders），否则 NoAction。同时清掉刷新时间，盘口恢复后立刻重新报价。
  2. 还没到 next_refresh_at_：NoAction。
  3. 有活跃订单：全部撤掉。这时刷新时间不更新，所以撤完以后立刻满足"到时间了"。
  4. 没有活跃订单：设 next_refresh_at_ = now + refresh_ms；计算中间价 mid = bid + (ask−bid)/2；买价 = mid×(1−bid_spread) 向下取整到价格精度，卖价 = mid×(1+ask_spread) 向上取整；数量 = order_amount 向下取整到数量精度。买单要求金额 ≥ 最小下单金额，且 金额+手续费 ≤ quote 预算；卖单要求数量 ≤ base 预算。

Shard 侧把它串成一个循环：

定时器(refresh_ms) 或 行情通知
  → Decide = CancelOrders  → 对每个订单 BeginCancel + CancelFromShard，awaiting_cancel_ = true
  → 撤单结果和回报陆续到达（A4/A5）
  → PostTradeEvent / OnAccountView 发现：awaiting_cancel_ 且无在途且无挂单
  → 立刻再 Decide = SubmitOrders（新的一对买卖单）

CancelFromShard（trading_account.cc:306）和下单是同一个模式：账户镜像任务入队（BeginCancel）+ CancelIntent 日志 + port->Cancel。如果撤单被交易所拒绝（订单仍在），OnAccountView 里会清掉 awaiting_cancel_，避免一直卡在等撤单的状态。

A7 超时与未知结果：查单兜底

每种结局怎么处理，见 B1。

  1. 账户线程 订单开始写网络时 OrderManager::Arm，2 秒后到期（trading/order_manager.cc:137）。只有"提交待确认、撤单待确认/未知、提交未知"的订单才会有查单计划。
  2. ScheduleOrderQuery 把唯一的 order_query_timer_ 设到最早的到期时间；对账中、私有流断开、停机中都不查。
  3. 到期 QueryDueOrder（trading_account.cc:998）：如果订单还在等 HTTP 结果，就先当作超时，写一条 Unknown 结果日志（原因：local response timeout），并走一遍 A4 的结果处理。然后 port->Query 查单。
  4. 查单结果 → QueryOrderResult，查到的订单状态（以及需要补查的成交）同样经 PersistAndApply 应用。查不到或查询失败不会编造拒单，只按 1、2、4…32 秒指数退避重查。

A8 断线与全量对账

完整的异常清单见 B 异常篇。

  • 私有流断开 → OnConnectionState(false)：取消对账和查单，Pause（ready=false、关准入、发布视图）。Shard 收到视图后不再下新单，已有订单原样保留。
  • 重新连上 → 走 A1 的第 7–8 步，完成全量对账后自动恢复准入（人工暂停的除外）。
  • 对账期间的私有回报会先缓冲；对账结束时缓冲非空或还有未处理的回报，就整轮重来，最多 3 次，超过就暂停。
  • 队列溢出、日志写失败、对账副本前后矛盾等情况都调用 Pause(reason)（trading_account.cc:1411）。原因可以在状态接口里的 error 字段看到。

A10 文件回放

  1. 主线程 Runtime::RunReplay（runtime.cc:405）→ ReadReplayFile：按文件顺序解析每条 ReplayRecord{target, time, MarketInput 或 TimerTick}。
  2. 每条记录 PostReplay 到目标 Shard，然后用 future 等它处理完，才解析下一条。所以全局严格串行，结果可复现。
  3. Shard 线程 Shard::PostReplay（shard/shard.cc:356）检查时间单调；行情走 Market::OnReplayInput（回放的快照可以在 Live 状态下整体替换盘口），定时 tick 走 CheckStale 或 OnStrategyTimer。策略的"现在"取记录里的时间，不读系统时钟。
  4. 处理结束后通过 MaybeCompleteReplay 回报完成；如果 Shard 遇到致命错误，就把错误状态返回给读文件的循环。

A11 停机

  1. SIGINT/SIGTERM 或控制面 stop → Runtime::RequestStop（runtime.cc:424）：所有账户 PrepareStop（进入静默，不再做新的对账和查单），所有 Shard RequestStop。
  2. Shard 线程 StopOnThread（shard/shard.cc:513）：停行情、停定时器，对所有挂单发撤单；每次回报或视图到达都再检查一遍，直到没有挂单为止，最多等 30 秒，超时会记一条错误。
  3. Runtime::Wait（runtime.cc:431）：等每个 Shard 停完 → 每个账户 PostFinalStatus（查一次最终余额并写日志）→ 账户 RequestStop → join 所有线程 → history_.FlushAndStop() 和日志收尾。

B异常篇：出错时系统做什么、怎么恢复

每种异常按三列写：异常是什么情况；行为是代码实际做了什么；处理与恢复说明会不会自动恢复、什么时候需要人工介入。先看 B0，大多数异常最后都会落到"暂停"这个状态。

B0 先理解"暂停"（Pause）

暂停时做了什么TradingAccount::Pause(reason)（trading/trading_account.cc:1411）：ready=false、关准入、把原因记进 error、给所有 Shard 发一份新视图。
Shard 的表现RunAccountDecision 的门控看到 ready=false 就直接返回，既不下单也不撤单。已经挂着的订单留在交易所，仍可能成交；成交回报照常处理。
暂停期间怎么撤单CancelFromShard 不检查准入，所以控制面的 cancel_all 和停机流程仍然能把撤单发出去。这是暂停期间唯一的主动撤单手段。
怎么恢复成功完成一次全量对账（AccountSync::FinishSync）就会自动恢复，人工暂停的除外。触发对账的方式有三种：私有流重连；60 秒周期定时器（只有上一次对账成功才会安排下一次）；控制面 resume_trading / sync_account_state。
所以有两类暂停要区分。周期对账能修复的，比如外部余额变动、账户队列溢出，60 秒内会自动恢复。对账本身会失败的，比如交易所查不到某笔订单、交易所上有本地不认识的挂单、日志写不进去，会一直停着，直到人工处理。

B1 重点：请求已发出，迟迟没有返回

这是最需要说清楚的一种情况：请求已经开始写 socket，但一直没有响应。系统不知道交易所到底收到没有，所以既不能当作成功，也不能当作失败。下面按时间顺序说明一笔下单会经历什么，撤单的流程相同。

t = 0     开始写 socket
          → 账户 OnWriting：submit_writing = true，写 SubmitWriting 日志，
            Arm 一个查单计划（2 秒后到期）；Shard 侧 MarkWriting
t = 2 s   查单定时器到期，订单仍是 PendingSubmit
          → QueryDueOrder 判定本地超时：写 SubmitOutcome(Unknown, "local response timeout")，
            账户副本标记 submit_unknown，并发出第一次查单
t = 5 s   HTTP deadline 到期（MakeRequest 设的 5 秒）
          → 因为已经开始写，结果分类为 Unknown → 写日志 → 通知 Shard → Shard 标记 submit_unknown
          （如果在这之前迟到的 200 回来了，就是 Confirmed → 订单变为 Accepted）
之后       查单按 1、2、4、8、16、32 秒退避，32 秒封顶，一直重查
          任何时候私有流的回报先到，都直接确定订单状态，查单计划随之撤销
结局行为处理与恢复
查到订单（已挂、已成交或已撤）查单结果和补查到的成交经 PersistAndApply 应用（trading_account.cc:1052），通知 Shard，订单得到确定状态自动恢复。Shard 的 Pending() 变为假，下一次决策照常进行
查不到（订单其实没到交易所），或查询一直失败代码不会编造拒单（见注释 "it never invents a rejection"），只会一直退避重查。订单保持未决，这个 Shard 一直不能下新单（PendingFor 把 PendingSubmit 和 Unknown 都算作在途）下一次周期对账会逐单查询，查询失败就暂停账户（"restored order query failed"），之后不会自动恢复。需要人工确认这笔单在交易所确实不存在，再处理

补充一点：2 秒的本地超时只更新账户副本，不通知 Shard。Shard 要到 5 秒的 HTTP 结果到达时才标记 Unknown。但 Shard 的门控对 PendingSubmit 和 Unknown 一视同仁，所以这段时间里两边的实际行为是一样的。

B2 下单与撤单请求的异常

异常行为处理与恢复
请求在本地队列里积压（限频等待中，或连接都在忙）下单等待超过 30 秒（PressureSim）或 5 秒（OnlineSim）还没发出，Drain 直接返回 NotSent（trade_client.cc:554）。撤单没有排队超时账户和 Shard 都释放占用、删除这笔订单，历史记一条 LocalRejected。策略到下个刷新周期重新报价
本地发送队列满port->Submit 返回 false：写 SubmitAbort，账户补一个 abort 镜像任务，Shard AbortSubmit，记 last_error="account submit unavailable" 并重置刷新时间下一次行情事件就会重试。撤单和查询在队列里有预留容量，不会被下单挤掉
连接失败，或在开始写之前出错NotSent（依据是 write_begin 还没被设置）同第一行，确定没发出去，直接释放
HTTP 5xx / 408 / 429 / 418，或 Binance 错误码 -1000/-1001/-1006/-1007Unknown（trade_client.cc:700）。429/418 还会让 RequestScheduler 暂停所有出口请求：有 Retry-After 就按它，否则 429 等 1 秒、418 等 2 分钟走 B1 的查单兜底；限频解除后排队的请求自动继续发送
下单被拒（其它 4xx）Rejected：订单进入终态，释放占用策略下个周期再报价。如果是规则类拒绝（精度、金额等），会每个周期重复被拒，需要看 last_error 和历史记录来排查
下单前就违反风控或交易所规则BeginSubmit 返回错误，请求不会发出；Shard 记 last_error 并重置刷新时间不影响账户状态。交易所规则在每次对账时更新
200，但客户订单号对不上或响应解析失败Unknown走 B1 的查单兜底
撤单返回非 200一律 Unknown，因为撤单失败也可能是订单已经成交或已经撤掉。记 CancelUnknown，安排查单由查单结果决定：已撤或已成交就进入终态。间隔两次查询都显示订单仍挂着，就判定为 CancelRejected（"order remains open after repeated query"），Shard 清除等待撤单状态，下一轮重新撤
撤单成功，但返回的剩余数量比本地少（有成交还没推送过来）保持撤单待确认和资金占用，不提前进入终态（trading_account.cc:779）自动：等私有流把成交和终态回报推过来
撤单因连接失败没有发出（NotSent）撤销撤单状态，订单仍是挂着的Shard 仍在等撤单，下一次行情事件会再做一次撤单决策，也就是每个行情事件都会重试

B3 交易所连接异常

异常行为处理与恢复
公开行情 WS 断开、30 秒读不到数据、或消息解析失败Fault → FeedDisconnected → Market 回到 Syncing 并清空盘口；如果之前是 Live，还会发 BookUnavailable。策略看到盘口不是 Live，就要求撤掉全部挂单（账户就绪时才会真的发出撤单）自动重连：退避从 250 毫秒开始翻倍，最长 30 秒（binance_feed.cc:506），然后重新走快照对齐。Live 后自动恢复报价。注意：这个退避在整个进程生命周期内不会重置，断过几次之后，每次重连都要等 30 秒
盘口过期（Live 状态下 5 秒没有更新）StaleLoop → 进入 Syncing 并取消 WS 读同上
序号缺口、盘口交叉或单边为空、增量缓冲满EnterSyncing(reason, reconnect=true) → Feed 断开同上，重连后从快照重新对齐
快照接口返回 429/418本轮失败，下次重连至少等 1 分钟（429）或 5 分钟（418）自动。如果配置的 max_snapshot_requests_per_run 用完了，行情协程会退出，这个 Shard 从此没有行情
私有流断开on_health(false) → OnConnectionState(false)（trading_account.cc:920）：中止进行中的对账，取消查单定时器，然后 Pause("private stream unavailable")。所有 Shard 停止决策，挂单留在交易所，未决订单也暂停查单自动重连：退避从 100 毫秒开始翻倍，最长 30 秒；连接保持超过 1 分钟后退避重置。连上后做全量对账，成功就自动恢复。断线期间要撤单只能用 cancel_all
私有流订阅被拒（鉴权失败）返回 PermissionDenied，不再重连（user_stream.cc:239）账户一直处于暂停状态。修好 API key 或权限后重启进程
交易所完全连不上（REST 和 WS 都不通）私有流断开 → 账户暂停（见上）。还没开始写的请求返回 NotSent，已经写出的返回 Unknown，进入查单；查单同样失败，按退避重试。行情也断开，盘口回到 Syncing交易所恢复后：行情自动重新对齐；私有流重连并全量对账，逐单确认所有未决订单，然后恢复交易。如果断网期间有订单其实没送到交易所，会落到 B1 的"查不到"那种结局，需要人工处理
只有 REST 不通，私有流正常账户不会暂停。新下单返回 NotSent 并被释放，撤单也发不出去（每个行情事件都会重试）REST 恢复后自动恢复。这段时间里旧挂单撤不掉，策略也挂不上新单

B4 本地资源与持久化异常

异常行为处理与恢复
可靠日志写失败（磁盘满、IO 错误）错误会一直保留：之后所有 Append 都返回同一个错误（order_journal.h 注释）。所有依赖日志的动作都会触发 Pause：下单意图、请求结果、回报、人工控制不能自动恢复，因为对账结果也要写日志。修复磁盘后重启进程，重启时从已提交的日志恢复
日志队列满（32768 条）Persist 返回 false。下单时就直接放弃这笔单（abort）；处理回报时就暂停积压消化后，通过对账恢复
账户任务队列满（8192 条）私有回报一条都不能丢，所以直接 Pause("account event queue overflow; state synchronization required")（trading_account.cc:1124）下一次对账时自动恢复：周期定时器、重连，或人工 sync_account_state
对账期间私有回报的缓冲满了放弃本轮对账并暂停（"private event buffer overflow during synchronization"）重连或人工 sync_account_state
观察历史（SqliteHistory）队列满记一个缺口（Gap），不影响交易不需要处理。回放模式下会等待队列空出，不会丢记录

B5 状态不一致

异常行为处理与恢复
外部余额变动（充值、提现、外部锁定）交易所推来 BalanceDelta → Pause("external balance delta requires reconciliation")60 秒周期对账自动恢复。Shard 的额度是启动时定好的，不会因为充值而增加
交易所上有本地不认识的挂单，或同一笔单的价格、数量、订单号对不上对账在 SyncOpenOrders 这一步暂停（"unrecognized or conflicting exchange open order"）需要人工处理：到交易所查清这笔单（必要时撤掉），然后 resume_trading
本地有未终结订单，但交易所查不到对账逐单查询失败 → 暂停（"restored order query failed"）需要人工处理，见 B1
三轮对账都被新到的私有回报打断暂停（"private events changed during three account sync attempts"）因为对账没有成功，周期定时器不会再安排。需要人工 sync_account_state，或等到私有流重连
账户副本出现矛盾（收到未知订单号的回报、查单返回了别的订单、NotSent 但订单已经开始写）Pause(具体原因)通过对账恢复。如果对账也对不上，就需要人工处理
Shard 侧状态矛盾（成交超出本 Shard 额度、不该出现的 NotSent 等）Shard 调 ReportShardError：账户关准入并暂停。这个 Shard 执行 StopFromError：停行情、撤掉自己的挂单、永久停止Shard 不会自己重启，需要重启进程。其它 Shard 等账户对账成功后自动恢复
策略计算溢出（定点运算报错）Decide 返回错误 → 该 Shard 执行 StopFromError检查策略参数和精度配置，然后重启

B6 进程级异常

异常行为处理与恢复
进程崩溃已提交的日志条目都还在，内存状态全部丢失重启后：Load 日志，重建账户和 Shard 两份状态 → 等私有流连上 → 全量对账，逐单确认未终结订单 → 都对得上就自动恢复。有两种情况会停在暂停状态：① "请求已发出、意图还没落盘"窗口里的订单，在交易所上会被当成本地不认识的挂单（见 D 节）；② 本地记了意图、但交易所从没收到的订单，查单会失败。这两种都需要人工处理
停机时交易所连不上Shard 的撤单发不出去，等 30 秒后放弃，记录 "shutdown left unconfirmed account orders"挂单可能还留在交易所，需要人工检查
OnlineSim 达到 max_submissions_per_runSubmitFromShard 返回 false，不再下单。上限设为 0 时，账户以只读验证方式运行，永远不就绪这是设计行为，用来保护 Demo 账户

strategy.h / .cc：策略（约 80 行）

职责
Decide(BookView, ExecutionView, now) → NoAction | CancelOrders | SubmitOrders，不做任何 IO，逻辑见 A6。ExecutionView 是 Shard 为策略准备的执行约束（活跃订单、预算、精度、手续费）。
规则
价格计算全部用定点数，并带溢出检查；买价向下取整，卖价向上取整，保证不会因为取整越过中间价。

trading_state.h / .cc：Shard 本地交易状态（约 400 行）

职责
本 Shard 的余额（初值来自分配额度，之后只随成交变化）、按资产汇总的占用、每笔订单的 Hold，以及一个只记录本 Shard 订单的 OrderManager。负责下单准入（BeginSubmit）、撤单（BeginCancel）、写出标记、结果和回报的应用，以及从日志恢复（RestoreJournal）。
线程
只由 Shard worker 写（头文件注释写明了这一点）
规则
余额只认成交。BalanceUpdate 这类账户级余额事件不改 Shard 余额，因为 Shard 只管自己那一份额度。任何矛盾都返回 DataLossError，导致这个 Shard 停止。

shard.h / .cc：Shard 外壳与事件入口（约 600 行）

职责
把 Market、Strategy、ShardTradingState 组装在一起，并提供所有跨线程入口：PostTradeEvent、PostTradeResponse、PostTradeWriting、PostAccountView、PostCancelAll、PostStrategyUpdate、PostStatus、PostReplay。这些入口都只做一件事：post 到本 Shard 的 io 上执行。
触发决策的地方
行情通知（OnMarket）、刷新定时器（OnStrategyTimer）、撤单全部完成（PostTradeEvent/OnAccountView）、策略参数更新。
停机
StopOnThread → 撤掉所有挂单 → 没有挂单或等满 30 秒 → CompleteStop 唤醒所有等待者。

C3 trading/：与交易所无关的交易核心

trading_event.h：交易事实

职责
LimitOrderRequest、Order、OrderStatus（PendingSubmit/Rejected/Accepted/PartiallyFilled/Filled/Cancelled）、OrderReport、Fill、BalanceUpdate（余额绝对值）、BalanceDelta（余额增减）。AccountEvent 是后四种的 variant，私有流、查单、对账产生的都是它。

trade_port.h：交易所抽象接口

职责
Submit/Cancel（带完成回调和写出回调）、Query/QueryTrades/QueryBalances/QueryOpenOrders/QueryRules、QueueHealth、Stop。TradeResponse 的四种结果见 A4。VenueRule 是交易所下发的交易规则。
约定
返回 true 表示本地有界队列接受了请求，完成回调稍后才到；返回 false 时不得调用完成回调。私有回报和完成回调各走各的路，到达顺序不保证。

client_order_id.h / .cc

职责
生成 hq + 32 位十六进制的客户订单号，随机数来自 OpenSSL RAND_bytes。

order_state.h / .cc：订单状态机（约 230 行）

职责
TrackedOrder 记录一笔订单的全部本地信息：状态、撤单阶段 CancelPhase（None/Pending/Unknown/Rejected/Confirmed）、submit_unknown、submit_writing/cancel_writing、已成交数量、已处理的成交 ID 集合（用于去重）。OrderState 只负责状态迁移，不做 IO。
规则
回报按时间戳防止乱序；同一成交 ID 只计一次；终态订单不再改变。

order_manager.h / .cc：订单索引与查单计划（约 220 行）

职责
包装 OrderState，加了三样东西：本地订单号到客户订单号的映射、按 Shard 分组的活跃订单集合（OpenFor/PendingFor）、查单计划（Arm/TakeDue/QueryFinished，2 秒首查，之后指数退避，上限 32 秒）。
线程
一个实例只归一个线程：Shard 和账户各有一个实例。

risk_limits.h / .cc：下单前风控

职责
静态函数 Check，检查顺序：配置里的价格和数量精度 → 最小金额 → 交易所实时规则 → 单笔金额上限 → 活跃订单总数、同交易对订单数、同计价资产挂单总值。
用在哪
只在 ShardTradingState::BeginSubmit 里调用，传入的是 Shard 自己的订单表，所以"活跃订单数"等限额是按 Shard 生效的（Shard 级覆盖值来自 ShardAllocation）。

funds_state.h / .cc：账户资金对账（约 420 行）

职责
账户级资金状态。交易所余额（free/locked）用来算可用额，成交推算出来的总额用来对账。公式：可用 = max(0, free − 交易所还没反映的订单占用 − 交易所还没反映的成交借记)。区分一笔占用"已被交易所 locked 覆盖"和"尚未覆盖"，避免重复扣除。
用法
Shard 已经按自己的额度准入过了，所以账户副本用 ReserveAllocated（不再检查可用额）；余额回报来了用 MatchesProjectedTotal 系列函数判断是否和成交推算一致。

order_journal.h / .cc：可靠日志（约 380 行）

职责
13 种 JournalKind，覆盖意图、撤销、请求结果、回报、成交、余额、人工控制、写出。SQLite 开 WAL + synchronous=FULL。Append 只入队；写线程最多等 250 µs 或凑满 256 条，一批一个事务，COMMIT 成功后才把回调 post 回调用方的 io。条目用自定义二进制格式编码（带格式版本号）。
线程
独立写线程，另有一个读连接给 Load/QueryControls 用。
规则
第一次写失败后就不再写入，之后排队的条目都收到同一个错误。

trading_account.h / .cc（+ _journal.cc）：账户（约 1700 行）

职责
每个交易账户一个实例。维护与交易所对账的副本（OrderManager + FundsState）、准入开关、任务队列；把交易所事实先写日志再应用；把结果、回报、视图分发给各 Shard；负责查单、暂停和人工控制。
线程
状态归 账户 worker。SubmitFromShard/CancelFromShard 是从 Shard 线程调用的。
锁
queue_mutex_ 只保护任务队列；state_mutex_（递归锁）在 Drain 执行任务和各种回调时持有，因为 TradePort 可能同步回调、发生重入；admission_gate_mutex_ 是读写锁，Shard 下单持读锁，开关准入持写锁；journal_mutex_ 保证日志序号和入队顺序一致。
队列
TryEnqueue 有容量上限（8192）；Drain 每批最多执行 64 个任务，然后让出线程，给 socket 和定时器执行机会。入队失败的处理一般是 Pause。

account_sync.h / .cc：全量对账（约 420 行）

职责
在启动、重连、人工同步和每 60 秒时运行：查规则 → 查挂单 → 逐单查单和成交 → 查余额 → FinishSync。用 generation_ 让上一轮还没返回的查询回调失效。对账期间收到的私有回报先缓冲。
结果
对账成功才会 EnableAdmission。OnlineSim 模式下如果 max_submissions_per_run=0，账户以只读验证方式运行，永远不就绪。

account_view_publisher.h / .cc：视图分发

职责
记录哪些 Shard、哪些资产"脏"了，Flush 时版本号 +1，只给脏的 Shard 发 AccountView。同时用 seqlock 发布每个资产的 PublishedAssetView（总额、可用、预算）。
现状
PublishedAssetView 目前只有测试在读，Shard 的预算读的是自己 ShardTradingState 里的数据（Shard::ReadAssetViews，shard/shard.cc:39）。

C4 venue/binance/：TradePort 的 Binance 实现

auth.h / .cc

职责
HMAC-SHA256 签名（BinanceHmacSignature）和时间戳；所有签名请求都带 recvWindow=5000。

rules.h / .cc

职责
把 exchangeInfo 解析成 VenueRule：交易状态、价格精度和范围、数量精度和范围、最小/最大下单金额。

request_scheduler.h / .cc：出口限频

职责
同一出口 IP 共用一个实例（所以是全局的）。按请求权重（挂单列表 80、余额/成交/规则 20、查单 4、下单撤单 1）累计每分钟用量，另外单独统计每 10 秒的下单次数。Reserve 原子地检查并预扣，不够就返回需要等待的时长。遇到 429/418 时，按 Retry-After 或默认值整体暂停。
线程
多个 REST lane 共享，内部用 mutex 保护。

trade_client.h / .cc：REST 交易客户端（约 790 行）

职责
实现 TradePort。包含 6 个优先级队列和 N 个 RestLane（每个 lane 一条 HTTP 长连接，加一个限频等待定时器）。每个 lane 跑一个 Drain 协程，循环"取最高优先级请求 → 限频 → 发送 → 分类结果"。查成交会自动翻页（每页 1000 条）。
线程
REST 在 Shard worker 上（如果绑定了 Shard），否则在自建线程上；私有流在 自建线程；所有完成回调都 post 到账户 io（OnAccount 包装）。
规则
队列里给撤单和查询预留了容量；下单在队列里超时就返回 NotSent；HTTP 结果按"能确定的才确定"的原则分类（A4 的表）。

user_stream.h / .cc：私有回报流（约 340 行）

职责
连 WS API，用签名订阅用户数据流，解析 executionReport、outboundAccountPosition、balanceUpdate、externalLockUpdate，通过 on_event 和 on_health 回调交给账户。断线自动重连，连接状态变化时通知账户。

D设计取舍与阅读提示

选择得到什么代价
资金按 Shard 预先切分，Shard 本地准入热路径不跨线程、不等待；一个 Shard 出问题不会占用别人的额度额度不能在 Shard 间动态调配；同一笔资金有两份账（Shard 一份、账户一份），两份必须由同一串事件推进
REST 连接跑在 Shard worker 上下单从决策到写 socket 不换线程HTTP 收发会占用 Shard 线程的时间；每个 Shard worker 各有一个 TradeClient 实例，REST 连接数在实例间分摊
一个 Shard 同时只有一批在途请求（Pending() 门控）状态简单，不会叠单撤单完成之前不会挂新单；一个周期内的报价更新受往返延迟限制
交易所事实先写日志、再应用崩溃后可以重建；人工控制可追溯每个回报都要等一次 SQLite 提交（批量提交摊薄成本）
下单意图日志"入队即发送"不把落盘延迟放进下单热路径SubmitIntent 入队后马上就 port->Submit，不等 COMMIT。所以存在一个短窗口：请求已经发出，但意图还没落盘。这个窗口里崩溃的话，重启后对账会在交易所上发现一笔本地不认识的挂单，账户随即暂停，需要人工处理（见 B5）
Shard 依赖具体的 TradingAccount 类调用直接，没有多余的间接层Shard 与账户耦合，单测 Shard 需要一个真实的账户对象；交易所那一侧则有 TradePort 抽象
出错一律 Pause 并要求重新对账宁可停也不带着错的状态继续交易任何一处队列满或日志失败都会让整个账户停止接单，需要监控 error 字段
建议的读代码顺序：shard/strategy.cc（80 行，先看清决策）→ shard/market.cc（状态机）→ shard/shard.cc:77（热路径）→ trading/trading_account.cc:152（SubmitFromShard）→ venue/binance/trade_client.cc:554（Drain）→ trading/trading_account.cc:944（PersistAndApply）→ shard/trading_state.cc（Shard 侧如何应用结果）→ trading/account_sync.cc（对账与就绪）。
