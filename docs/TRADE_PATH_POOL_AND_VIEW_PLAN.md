# 下单链路：账户视图、执行器与 REST 队列改造

## 问题与范围

1000 个 Shard 共用一个账户。现有压测中，账户任务入队到开始处理为 p50 58 µs、p99 2.947 ms；REST 入队到取出为 p50 155 µs、p99 5.520 ms。行情触发下单到模拟交易所收到完整请求为 p50 331 µs、p99 6.224 ms。这些数据来自本地压力器，不能作为真实交易所延迟。

两个已定位的阻塞：

- `AccountViewPublisher` 把共享 USD 的变动合并 100 ms 后，在账户 IO 线程逐个构造并投递 1000 份 `AccountView`；一次占用约 2.7–5.3 ms。等待期间账户任务和 REST 发送均不能推进。
- REST 只有 4 条持久 HTTP/1.1 连接；每条连接收到上一请求的响应后才可发送下一请求。所有连接忙时，请求必须等待。现有单队列还在每次取单时线性扫描优先级。

第一轮只改这两处。账户的串行风控、资金预留、日志意图先入队再发送、回报处理顺序保持不变。账户任务队列的常态等待在第二轮继续分析，不靠移动计时点掩盖。

## 方案

### 1. 共享资金视图改为按需读取

- 账户线程仍独占 `FundsState` 和 `OrderManager`。在账户一次状态变更完成、调用 `FlushViews()` 时，为受影响的共享资产发布一份带版本的只读快照（总额、可用额、预算）。Shard 只能读取快照，不能跨线程访问账户的可变对象。
- 共享资产变动不再把所有 Shard 标为 dirty，也不启动 100 ms 的全量视图定时器。Shard 在策略决策和状态查询时读取其 base/quote 资产的最新快照。
- 本地订单状态变化仍构造并投递对应 Shard 的 `AccountView`。这条通知继续唤醒等待撤单、回报或停机收尾的 Shard；普通共享资金变化不唤醒全部 Shard。
- 初始化和日志恢复后先发布快照，再允许 Shard 决策。全局 ready/pause 等少见状态变化保留原来的通知语义。

### 2. REST 待发队列整理与连接数验证

- 保留每条连接至多一个在途 HTTP/1.1 请求。现有 `StartDrains()` **原本已经**启用空闲连接，本轮没有改变连接复用和请求并发模型；请求在所有连接忙时仍须等待上一请求的响应。
- 将单个 `deque` 的线性优先级扫描改为各优先级 FIFO 队列，维持现有取消、查单、下单顺序、容量保留、限速、超时和 Unknown/NotSent 语义。多页成交查询重新入队时保持原来的优先处理方式。
- 连接数仍由 `rest_connections` 配置。本地压测比较 4/8/16/32；真实 Demo 的连接和限速配置不因本地压力器结果自动改变。若所有连接持续繁忙，必须以并发容量或请求到达率解释排队，不能承诺仅换队列便达到 20 µs。

## 实施与验证

1. 改共享资产快照与 Shard 读取；检查撤单后续策略、停机撤单、状态接口、日志恢复。
2. 改 REST 优先级队列与定时器唤醒；验证现有空闲连接调度、队列满、限速、超时、停机、断线以及查询分页。
3. 编译 Release，运行直接覆盖快照一致性的测试、连接池端到端回归、现有交易端到端测试及 1000 标的压力器。压测必须 `valid=true`，订单与回报数量一致。
4. 对照账户等待、REST 入队到取出／开始写、行情到交易所收完整请求的 p50/p99，并记录连接数和队列峰值。若未达到账户 10 µs、REST 20 µs 目标，报告剩余等待的确切阶段，不扩大本轮改动范围。

此前 4 连接运行中，账户等待 p50/p99 为 58 µs / 2.947 ms，REST 入队→取出为 155 µs / 5.520 ms，行情发出→交易所收单为 331 µs / 6.224 ms。视图改造去掉了每 100 ms 的 1000 Shard 批量发布；最终版本三组的 `shared_view_flush_trace.csv` 均只有表头。4 连接下账户等待尾部下降，但中位数及 REST 排队仍有波动；不同运行的微秒级结果不能当作严格 A/B 因果结论。

**第一轮达成情况：**共享视图扇出已移除；REST 方面只完成队列选择和定时器整理，没有实现能消除连接占满等待的新调度或并发机制。默认 4 连接的 REST 入队→取出 p50 从此前 155 µs 变成 1.082 ms，整条行情→收单 p50 从 331 µs 变成 1.281 ms，不能称为性能优化成功。16 连接改善了本地首批下单的中位数，但属于提高并发容量的配置实验，未解决 p99，也未改变默认配置。

连接数增加使更多请求立即取出，中位数改善；本次 1000 标的场景中，16 连接的行情→收单 p99 最低，32 连接的全体 POST p99 最低，但前者到后者使账户等待和首波发送尾部变差。模拟交易所的请求处理队列 p99 仍约 106–120 ms，响应回来前连接无法复用。因此保留默认 4 连接作历史对照；本地 1000 标的容量探索可用 16 连接，不能直接用于真实 Demo 配置。目标 10/20 µs 尚未达到；下一轮应分别定位账户执行器等待与交易所响应导致的连接占用。

## 第二轮：隔离账户与 REST 执行路径

第一轮在默认 4 连接下没有加速。原来账户、REST socket 和约 125 个 Shard 共用一个 `io_context`；每条 REST 连接在收到响应前不能接下一单。实际 2000 笔行情触发下单约在 117 ms 内入队，最密的 1 ms 有约 60 笔，仅替换队列容器无法消除连接占满和工作线程唤醒等待。

第二轮实施：

1. `Runtime` 为账户分配独立 `io_context`，Shard 继续使用自己的工作线程；账户仍串行执行风险检查、资金预留、订单状态变更和日志意图入队。账户工作线程处理事件后最多再轮询 50 µs，接住紧邻的跨线程下单任务，随后睡眠；200 µs 试验尾延迟更差，已撤回。
2. `BinanceTradeClient` 将 REST 待发队列、签名和 HTTP socket 移到独立 I/O 工作线程。账户线程在有界队列预留位置后投递具体请求；REST 线程只向空闲连接派发，每条连接仍只允许一个在途 HTTP/1.1 请求。写入通知和 REST 响应投递回账户线程，账户状态始终只有一个写入者。
3. 保留取消／查询优先级、限速、队列超时、分页重新入队、停止时 `NotSent` 与已写请求 `Unknown` 的语义。修复了分页重新入队时未恢复队列计数的问题，端到端分页测试覆盖此路径。停止时先取消在途 REST 请求并清空待发队列，所有连接协程退出后才释放账户执行器的保活对象；新增测试逐一核对已接收请求恰好回调一次。

第二轮 Release 本地压测均为 1000 标的、30 秒、3800 下单、3600 撤单、400 成交，全部 `valid=true`。下表的“第一轮”与“第二轮”是独立运行，微秒级差异有运行波动；第二轮 50 µs 轮询版本的原始 trace 分别在 `/tmp/hpoll4-20261012`、`/tmp/hpoll16-20261012`、`/tmp/hpoll32-20261012`。

逐单关联最终运行的 2000 笔行情触发下单：Shard 调用 `TrySubmit` 的相邻请求间隔 p50 为 6 µs，而账户开始处理的相邻间隔 p50 为 18 µs。账户开始处理→REST 入队只有 p50 4 µs、p99 35 µs；等待主要发生在突发请求进入单账户串行队列之前。REST 入队→派发为 p50 26 µs、p99 644 µs，派发→开始写只有 p50 3 µs、p99 43 µs。新 REST 工作线程增加一次跨线程投递，因此 16 连接下 REST 中位数由第一轮的 <1 µs 增至 24–26 µs；本轮收益集中在尾部，不能把中位数也称为改善。

`account_view_publisher_test`、`trade_client_stop_test`、`trade_chain_smoke`、完整 `trade_end_to_end` 均通过；其中完整测试覆盖分页查成交、失联恢复、限速后的未知订单、日志故障和撤单。本地 C++ 压测默认改为 16 连接，历史对照须显式指定 `--rest-connections 4`；真实 Binance Demo 配置未调整。

账户等待 10 µs、REST 等待 20 µs 的原目标仍未达到。账户仍须顺序处理同一账户的资金和订单，REST 连接仍须等上一请求的响应。特别是 4 连接下全部 POST 的 p99 恶化，说明突发量超过现有连接容量；不能用首批行情单的改善概括全部订单，也不能靠更改计时边界消除等待。
