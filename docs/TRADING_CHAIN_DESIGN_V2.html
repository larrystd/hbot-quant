1. 现状、目标与差距

当前 schema_version: 2 已允许多个 Shard 共用一个 TradingAccount。公开行情经 Shard::OnMarket() 驱动策略；Shard::RunAccountDecision() 把挂单、撤单交给账户。账户在 `trading_account.cc` 中完成风险检查、调用 `client_order_id.cc` 生成随机 client_order_id、预留资金、记可靠意图、调用 TradePort；`trade_client.cc` 负责签名 REST 和有界异步发送队列；`user_stream.cc` 收私有 WS。REST 结果、私有事件和查询结果回到账户，先记 OrderJournal，再应用到 OrderState、FundsState 和账户视图。可靠日志和回放在 `trading_account_journal.cc`；启动、断线和周期全账户同步由 `AccountSync` 执行；`AccountViewPublisher` 负责构造并推送 Shard 视图。两者由 TradingAccount 组合持有，运行在账户的同一 I/O 线程。

V1 外部链路曾在本机模拟交易所的 1000 标的、30 秒 case 中验证；V2 已重新运行同一 case，并用两笔 BTCUSDT 虚拟资金成交验证了真实 Binance Spot Demo 的挂单、私有成交回报、非空成交查询、余额对账及重启。配置值 online_sim 仅允许固定 Binance Demo 域名、Demo 凭据、一个账户和一个标的；示例默认零笔挂单，单次上限一笔。

2. 两条主链与补偿链

一个 Shard 对应一个行情标的；一个交易账户可以服务多个 Shard，但只维护一份订单投影、资金投影、交易客户端和私有回报连接。以下 OrderJournal 的两个方框指向同一个 order_journal.sqlite；SqliteHistory 指 history.sqlite，是另一份库。

4. 订单跟踪与取消换单

4.1 一张订单、两组状态

OrderManager 以 (account_id, client_order_id) 查订单，保存 exchange_order_id、所属 Shard、标的、方向、原始数量、累计成交、剩余数量、成交 ID 集合、来源 bench_seq 和最近的回报版本。订单生命周期与撤单请求是两组状态，避免把“请求撤单”误写成“订单已撤”。

维度典型状态进入条件
订单PendingSubmit → Accepted → PartiallyFilled → Filled已提交可靠意图；随后收到匹配的 REST 成功响应、私有回报或有效查询事实；成交按 ID 去重
订单拒绝PendingSubmit → Rejected明确的交易所拒绝或经查询确认的拒绝；本地队列拒绝单独记 SubmitAbort
撤单请求None → PendingCancel → Confirmed / Rejected / Unknown撤单意图持久化后等待交易所结果；撤单期间订单仍可能部分或全部成交
网络结果Queued、DispatchStarted、ResultUnknown、DefinitelyNotSent用于判断是否可本地撤销请求；它不是交易所订单状态

明确匹配 client_order_id 和订单参数的 REST 成功响应可以作为交易所确认；私有 WS 可能先到，不能被晚到的 REST 超时覆盖。TradePort::Submit/Cancel 返回 true 只表示本地队列接纳。发送队列中的命令在客户端停机或连接失败时，需要给账户一个“确定未发出”或“可能已发出”的结果；后者始终按未知处理。

OrderManager 按账户维护到期队列并给出下一到期时间，TradingAccount 只持有一个 steady_timer 调用 TakeDue()，不为每笔订单创建 socket 或线程。到期通过请求调度器查询原 client_order_id，并查询该单成交；查单无结果或超时不自动视为拒单。撤单未知期间不重复发撤单；确认撤单、成交终态或确认订单仍在账并允许重试后，Shard 才继续决策。

本轮 OrderManager 提供状态变化和查询计划，TradingAccount::ApplyEvent() 在日志提交后根据状态变化调整 FundsState、记录历史并发布 Shard 视图。OrderManager 不直接写资金或 SQLite，可单独测试订单状态。资金效果对象化尚未实现，继续由账户编排代码显式处理。

4.2 关键函数的改动

入口当前V2
Shard::OnMarket()外部模式由行情或定时器直接调用策略；Paper 另走 TryMarket()删除 Paper 的 TryMarket() 与直接撮合分支；行情只驱动策略，不跟踪真实订单

TradingAccount::ProcessSubmit()自己建 ID、OrderState、FundsHold、日志和发包风控与资金占位后调用 OrderManager 建订单；可靠意图提交后交 TradePort；账户继续编排资金和日志

5. 资金、SQLite 与故障边界

5.1 FundsState 同时处理交易所余额和本地占用

交易所的 free/locked/total 是外部账本，FundsState 是本地安全投影。买单预留报价资产和可确定的手续费余量，卖单预留基础资产；手续费若可能从第三种资产扣除，需要相应余额或风险余量。PendingSubmit、活动单、PendingCancel 和结果未知都保留占用。部分成交缩小剩余预留，并在余额事件反映成交前保持临时扣减。

V2 将当前 `FundsHold.reflected_by_venue` 的布尔语义改成可核对的覆盖金额／版本：

text
可用于新订单的资产金额
  = max(0, 最近可信交易所 free
            − 尚未被该余额快照覆盖的本地订单预留
            − 尚未被该余额快照覆盖的成交与手续费扣减)

例如账户原有 100 USDT，订单 A 待提交预留 60，可再用 40；若交易所确认 A 在账、可信余额变为 free=40, locked=60，A 的 60 已包含在交易所锁定中，不再从 40 重复扣减。REST 接受本身不足以证明余额已更新。本轮用每笔覆盖金额、每资产尚未覆盖的预留和余额版本做保守扣减；旧版本快照不能覆盖新状态。全账户同步完成后，才依据核实过的余额快照结算待反映成交扣减。

FundsState 另保存一份独立于交易所余额回报的资产总额：新状态目录以配置的全部非零资产为基线，仅以已确认成交的基础资产、报价资产及手续费资产变化推进。私有余额事件按事件时间与成交时间比较，避免“REST 查成交先于较早私有余额回报”时误报；全量账户查询及停机最终查询仍要求与最新成交投影完全相等。未配置的非零资产、真正账户外资金变动或无法解释的余额会暂停新单。第三资产手续费和账户外借记已在本机模拟交易所用例中验证；真实 Demo 的这些故障场景仍未验收。重启同一状态目录必须保留最初的配置基线，不能改成当前余额，否则重放成交会重复计算。

5.2 两份 SQLite 的写入位置

数据库文件写入时机与用途
可靠日志order_journal.sqlite，实现为 `OrderJournal`发包前将 SubmitIntent／CancelIntent 放入有界写队列，不等待 SQLite COMMIT；REST 结果、私有订单／成交／余额事件仍在应用前提交。SQLite WAL + synchronous=FULL 用于已写入记录的持久性。
观察历史history.sqlite，实现为 `SqliteHistory`命令进入发送链路后异步记历史；回报应用后异步记订单、成交、余额与阶段。可查询和核对历史序号；写入成功不代表交易所成功，写入失败不能用这份库恢复订单。

账户日志序号必须连续。意图入日志队列后可立即进入 TradePort；发送队列明确拒绝时异步记 Abort，并立即撤销未发出的本地状态。订单超时从实际开始写 socket 计时，不能把仍在交易客户端队列中的订单提前当成交易所结果未知。意图提交失败时 Quill 记录带 client_order_id 的错误、账户暂停新单，并对仍未决的订单启动查单；已入队不能当作未发出。会改变订单或资金的回报仍先可靠提交再应用、发布账户视图、写观察历史。进程在意图 COMMIT 前崩溃可能丢失本地 client_order_id：启动同步可发现陌生活动单并暂停，但已终结订单仍需交易所历史排查；当前实现不保证这个窗口的自动恢复。

5.3 同步和停机

启动顺序：OrderJournal 回放订单与占用 → 建立私有 WS 并缓存事件 → 查询交易规则、全账户活动单、未决订单、逐笔成交和余额 → 将状态变化记日志并归并 → 消费或重新同步缓存事件 → 差异消除后进入 Ready。私有 WS 断线、余额矛盾或定期检查重用全量同步；未知订单先按单查询。交易所出现本地未记录的活动单、资金无法解释或查询不完整时保持暂停。

正常停机先停止新单和策略定时器，再管理已知订单，继续收回报和查单直至确认或达到期限；未决意图保留在日志中供下次启动查询。不能把“撤单已入队”写成“撤单成功”。
