# hquant 端到端正确性与性能摸底（2026-10-06）

## 范围与环境

本次测量覆盖 `ReadReplayFile → Runtime → Shard → Market → PaperExchange → Strategy → Executor → SqliteHistory`，并用本地 Binance REST/WebSocket 模拟服务覆盖公开行情接入、Control 和 SQLite 历史。构建为 Bazel 9.2.0 的 `--config=release`（`-c opt -g1`）；机器为 Apple M2 MacBook Air（8 核、24 GB 内存），macOS 26.1。每个性能场景各运行 3 次带计时探针的基准进程和 3 次正式 `hquant_server` 进程，表中为各指标的中位数。完整原始结果见 [perf_results_2026-10-06.json](perf_results_2026-10-06.json)。

当前入口只实现本地 PaperExchange 下单。Binance 接入只消费公开行情，因此以下“端到端正确”指当前实现的完整运行路径，不代表真实交易所私有订单回报或真实网络吞吐已经验证。

## 正确性结论

`bazelisk --batch test --config=release //...`：2 个 Bazel 测试目标通过，其中黑盒端到端套件含 6 个用例。`bazelisk --batch test --config=asan //hquant/test:end_to_end` 也通过；该配置同时启用 AddressSanitizer 和 UndefinedBehaviorSanitizer。

| 场景 | 核对内容 |
| --- | --- |
| 双 Shard 复杂回放 | BTC/ETH 独立订单与余额；盘口快照、差分、公开成交、定时刷新、部分/完全成交、手续费、撤单、盘口过期、深度序号缺口与重连缓冲；按整数账本重算每笔余额和可用资金，并断言具体成交价格、数量和最终资金。 |
| 派发与交易所拒绝 | 命令已派发仍可收到模拟交易所拒绝；不得误记为接受或成交。 |
| 历史背压 | 3000 次刷新产生预期的 42012 条记录；检查逐条 Shard 序号连续、无 `history_gaps`。 |
| 本地 Binance 协议 | 本地 REST 快照与 WebSocket 深度/成交，经过真实服务的行情、撮合、Control `status/history/set_strategy/stop` 到 SQLite；验证策略版本、旧版本拒绝、改价后的成交价与资金。 |
| 错误输入 | 回放时间乱序、十进制精度超限均明确失败，不作为成功运行继续。 |
| 性能矩阵完整性 | 每次基准测量都要求 Shard 实际处理数等于输入数；SQLite 记录总数和各事件类型数量匹配由工作负载推导的独立预期值；各 Shard 序号连续、无缺口，正式服务输出与基准输出一致。 |

高频刷新测试曾暴露实际问题：历史队列满时回放继续运行，`refresh1` 的 280012 条应写记录中只写入 131586 条，`mixed4` 的 466696 条中只写入 398848 条，且吞吐数字因此虚高。现在文件回放在队列满时等待写线程腾出空间；复跑的 12 次基准测量和 12 次正式服务运行均写入全部预期记录，`history_gaps` 为 0。实时公开行情仍采用原有的“队列满则记录缺口”策略，详见下方限制。

## 吞吐与延迟

这里的“10 万”指整个回放文件中**10 万条合成盘口差分消息**，不是 10 万档深度、10 万只股票，也不是每秒收到 10 万条。`market1` 把这 10 万条送到 1 个币对；`market4` 平均分给 4 个币对。每条消息只更新固定买价 tick 9999 和固定卖价 tick 10001 上的数量，没有价格移动、公开成交或真实网络接入。生成器给这 10 万条消息标了 `at_us=1..100000`，即 0.1 秒的模拟时间；回放不按这些时间戳限速，而是每投递一条就等待它处理完成。这组行情没有触发周期报价刷新或成交，`market1/4` 分别只产生 12/48 条启动和停止相关的历史记录。因此下面的 QPS 主要测量简化盘口差分的读取、路由与处理，不能直接当作完整交易链路或美股、A 股生产行情容量。

QPS 是每秒完成的**输入投递数**，包括每个 Shard 的 3 条建盘输入；正式服务 QPS 使用进程外壁钟时间，包含启动、读取回放、退出和历史刷新。基准 QPS 只覆盖读取回放到所有输入处理完成，不包含最终历史刷新。`回调延迟` 从 `PostReplay` 开始，到对应账户事件都处理完毕的回调结束；此时 SQLite 事务可能尚未提交。`落盘延迟` 从 Shard 开始处理输入，到该输入产生的历史记录事务提交；只对实际产生的历史记录统计。

| 场景 | 投递数 / 历史记录数 | 正式服务 QPS | 基准 QPS | 回调 p50 / p95 / p99 | 落盘 p50 / p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `market1`：1 Shard，10 万条合成盘口更新 | 100003 / 12 | 54549 | 55385 | 17.0 / 20.7 / 24.7 µs | 0.451 / 0.544 ms |
| `market4`：4 Shard，合计 10 万条合成盘口更新 | 100012 / 48 | 54050 | 55170 | 17.0 / 21.0 / 25.0 µs | 0.509 / 0.635 ms |
| `refresh1`：1 Shard，2 万次报价刷新 | 20003 / 280012 | 19415 | 21681 | 20.5 / 134.0 / 154.2 µs | 28.0 / 29.1 ms |
| `mixed4`：4 Shard，10 万条行情和定时输入 | 100012 / 466696 | 40644 | 44652 | 17.3 / 25.6 / 91.0 µs | 39.9 / 43.0 ms |

`market1/4` 只有 12/48 条历史记录，落盘分位数样本很少，只能视为该次测量值。高写入量的正式服务历史写入约为 `refresh1` 27.2 万条/秒、`mixed4` 19.0 万条/秒。基准与正式服务的 QPS 不能直接相减当作探针开销：基准包含每条延迟采集与结果向量，正式服务包含进程启动和关闭，两者计时边界不同。

3 次正式服务 QPS 的范围分别为：`market1` 42182–54731、`market4` 53345–54082、`refresh1` 18974–19431、`mixed4` 40581–40665。低写入量的进程计时受启动和系统调度波动影响较明显；稳态输入处理能力可参考基准 QPS。

## 分段延迟

以下是带探针基准进程的逐输入分布，单位为 µs，单元格为 **p50 / p99**。`Post→Shard` 包含 Runtime 路由、Asio 投递与队列等待；`Shard 输入处理`包含行情、模拟撮合、策略与命令派发；`处理结束→完成回调`包含已排队账户事件的处理与下一次 Asio 调度；`完成回调→future.get`包含 promise 通知与回放线程唤醒。

| 分段 | `market1` | `market4` | `refresh1` | `mixed4` |
| --- | ---: | ---: | ---: | ---: |
| Post→Shard | 2.33 / 6.17 | 2.33 / 6.38 | 2.71 / 5.38 | 2.71 / 5.17 |
| Shard 输入处理 | 0.54 / 0.71 | 0.54 / 0.79 | 2.71 / 120.83 | 0.46 / 4.29 |
| 处理结束→完成回调 | 12.38 / 16.21 | 12.38 / 16.50 | 12.92 / 139.75 | 11.79 / 78.25 |
| 完成回调→future.get | 1.63 / 4.17 | 1.67 / 4.17 | 2.04 / 4.38 | 2.04 / 4.42 |
| 整条输入回调 | 16.96 / 24.67 | 16.96 / 25.04 | 20.50 / 154.17 | 17.33 / 90.96 |

历史写入路径另按**每条记录**和**每批事务**统计，单位见行名。`落盘`的起点为 Shard 开始处理输入，终点为 SQLite 事务提交。

| 分段（p50 / p99） | `market1` | `market4` | `refresh1` | `mixed4` |
| --- | ---: | ---: | ---: | ---: |
| 历史入队，每记录 µs | 0.08 / 1.92 | 0.08 / 9.75 | 0.08 / 97.63 | 0.04 / 0.21 |
| SQLite 写事务，每批 ms | 0.129 / 0.306 | 0.222 / 0.390 | 0.198 / 1.180 | 0.285 / 1.122 |
| 输入→落盘，每记录 ms | 0.451 / 0.544 | 0.509 / 0.635 | 28.005 / 29.056 | 39.913 / 43.000 |

每次运行都核对这些分段的样本数：逐输入分段与投递数一致，历史入队与记录数一致，SQLite 写事务与批次数一致。各行来自不同总体且有嵌套；例如策略派发会写历史，账户事件也会写历史。分段 p99 不能相加得到整条输入的 p99。

## 阶段瓶颈与采样证据

| 场景 | 阶段测量中位数 | 结论 |
| --- | --- | --- |
| `market1` | 读取并解析同一文件的独立基线约 48 ms；10 万条 Shard 输入处理累计约 57 ms；回放壁钟约 1806 ms，SQLite 写事务累计约 1 ms。输入处理 p50 为 0.54 µs，处理结束到完成回调 p50 为 12.38 µs。 | 额外的 Asio 完成回调投递和逐条 `future.get` 等待主导吞吐。4 Shard 与 1 Shard QPS 接近，因为回放驱动没有并行灌入多个 Shard。 |
| `refresh1` | SQLite 写事务累计约 937 ms；回放壁钟约 923 ms；历史入队累计约 515 ms（含队列等待），队列峰值 8192/8192；决策及命令派发 p99 约 121 µs。 | 历史写入达到持续上限，队列背压进入 Shard 处理与账户事件处理尾部；落盘 p99 为 29.1 ms。 |
| `mixed4` | SQLite 写事务累计约 2247 ms；回放壁钟约 2240 ms；队列峰值 8192/8192；处理结束到完成回调 p99 为 78.25 µs。 | 同样受 SQLite 写入限制；落盘 p99 为 43.0 ms。 |

`refresh1` 的持续写入约为 30.3 万记录/秒，满队列的 8192 条约需 27 ms 才能排空一轮，与 29.1 ms 的落盘 p99 接近。`mixed4` 约为 20.8 万记录/秒，对应约 39 ms，也与 43.0 ms 的落盘 p99 接近。单批写事务 p99 约 1.1–1.2 ms，因此高落盘延迟主要发生在等待队列，而非单批提交本身。无成交的盘口差分中，模拟撮合 p99 约 0.13 µs，决策、派发及命令记录 p99 约 0.46 µs；这不能代表成交密集时的撮合成本。

`refresh1` 的账户事件处理 p99 约 95.9 µs，单条历史入队 p99 约 97.6 µs；这与策略、派发 p99 约 121 µs 的长尾相互印证，长尾主要由满队列等待传导，而非策略计算本身。

macOS 无 Linux `perf`，使用系统 `/usr/bin/sample` 以 1 ms 间隔采样。调用栈采样在增加分段计时向量前完成，经过的回放与 SQLite 路径相同。40 万条合成盘口更新的采样中，主线程 2130/2197 个样本停在 `future.get` 的条件变量等待；历史写线程 2197/2197 个样本空闲。10 万次报价刷新的采样中，历史写线程 2605/2614 个样本在 `WriterLoop`，其中约 1994 个样本位于 `WriteBatch`，主要深入 `sqlite3_step` 的插入路径；提交路径还能看到 `pwrite`、`fsync`。这些是采样栈上的包含关系，不能当作独立耗时相加。阶段计时本身也存在嵌套与并行，表内毫秒数不能相加得到总壁钟时间。

## 设计判断与后续优化方向

1. 当前确定性回放按每条输入等待 Shard 及账户事件完成，便于严格顺序和可复现结果；它的约 5.5 万输入/秒低写入量上限主要来自第二次 Asio 投递和回放线程唤醒。优先验证在没有待处理账户事件时能否直接完成回调；若要提高多 Shard 离线回放吞吐，还需维持每 Shard 顺序并做有界流水化。
2. 报价频繁撤挂时，每次刷新会产生 14 条历史记录。SQLite 使用 64 条一批的事务写入；高写入量已使队列触顶。当前 `history_records` 同时定义了 `UNIQUE(run_id, shard, shard_sequence)` 和相同列顺序的显式索引，写入时需维护两棵等价索引，这是可确认的写放大。应先对移除重复索引、复用 prepared statement、批次大小分别做 A/B 测量；任何 WAL/同步策略变化都要同时验证崩溃后的持久性语义。
3. 文件回放现可在写队列满时背压并保持历史完整。实时公开行情目前优先保持 Shard 响应，满队列会落 `history_gaps`；高压下实时路径的“全量历史可追溯”尚无保证。实盘级要求需要单独设计持久化缓冲/背压与重连恢复，并用真实交易所私有订单回报测试。当前代码没有真实下单路径。

## 复现

在仓库根目录运行：

```sh
bazelisk --batch test --config=release //...
bazelisk --batch test --config=asan //hquant/test:end_to_end
bazelisk --batch build --config=release //hquant/bench:replay_bench //hquant/src:hquant_server
python3 hquant/bench/run_matrix.py --fixtures-root /tmp --output /tmp/hquant-perf.json --repeats 3
```

在 macOS 上复现调用栈采样（先生成足够长的回放文件）：

```sh
python3 hquant/bench/make_replay.py /tmp/hquant-profile --workload refresh --events 100000 --shards 1
mkdir -p /tmp/hquant-profile/state
bazel-bin/hquant/bench/replay_bench /tmp/hquant-profile/config.yaml /tmp/hquant-profile/state > /tmp/hquant-profile/result.json &
bench_pid=$!
/usr/bin/sample "$bench_pid" 3 -file /tmp/hquant-profile/sample.txt
wait "$bench_pid"
```

原始数据的 `benchmark_runs` 和 `production_runs` 含每次运行的分布、阶段计时、CPU 时间、最大 RSS、SQLite 行数/类型数及各 Shard 序号。吞吐与延迟是这台机器在这些确定性回放负载上的摸底值；真实网络、交易所响应和行情突发分布需要另测。
